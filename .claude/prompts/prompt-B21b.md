## 목표

**실시간 팬아웃을 실제로 연결한다.**

B21이 `OfficeHub`·WebSocket 라우트·`broadcastAfterCommit`을 다 만들었는데
**아무도 그것을 호출하지 않는다.**

```
$ rg broadcastAfterCommit worker/
worker/realtime/broadcast.ts:15:export function broadcastAfterCommit(
worker/realtime/hub.test.ts:17,189   ← 테스트뿐
```

`worker/index.ts:66`도 `_ctx: ExecutionContext`로 받아만 두고 라우트에
넘기지 않는다.

결과: 소켓은 연결되는데 **프레임이 하나도 안 나간다.** F7이 두 브라우저로
검증하다 발견했다 — 두 번째 창이 5초 폴링으로만 갱신됐다.

**이건 B21 구현자 잘못이 아니라 내 수용 기준의 공백이다.** "소켓 2개가 같은
이벤트를 받는다"만 요구해서, 테스트에서 `broadcast()`를 직접 부르면 통과했다.

## 무엇을 하나

### 1. `ExecutionContext`를 라우트까지 전달

`worker/index.ts`와 `worker/http/router.ts`가 핸들러에 `ctx`를 넘기게 해라.

**기존 핸들러 시그니처를 최소로 바꿔라.** 라우트가 30개다 — 전부 강제로
고치게 만들지 말고, 필요한 라우트만 쓸 수 있는 형태가 좋다.

### 2. 커밋 후 방송

`events`를 발행하는 모든 라우트가 **D1 커밋이 성공한 뒤** 방송해라.

**순서가 핵심이다:**

- 커밋 **전에** 방송하면 롤백된 변경이 화면에 뜬다
- 방송 실패가 **응답이나 커밋에 영향을 주면 안 된다.**
  `ctx.waitUntil`로 넘겨라. 프레임을 잃어도 D1에 이벤트 행이 남아 있고
  클라이언트가 `officeSeq` 갭을 감지해 캐치업한다 — **그게 설계다**
- **변경이 0행이면 방송하지 마라.** 조건부 `publish()` 가드로 이벤트가
  안 나갔으면 방송도 없어야 한다. 아니면 아무 일도 없었는데 화면이 깜빡인다

### 3. 어느 라우트가 대상인가

`publish()`를 호출하는 곳 전부다. 직접 찾아라 — 목록을 내가 주면 빠뜨린 것이
생긴다.

**웹훅(MO·리포트)도 포함이다.** 고객 문자가 실시간으로 떠야 이 도구가
의미가 있다.

## 반드시 지킬 것

**봉투를 새로 만들지 마라.** `publish()`에 넘긴 것과 **같은 값**이 나가야
한다. 두 벌이 되면 HTTP 캐치업과 WS 프레임이 달라져 클라이언트가 갈린다.

`officeSeq`는 DB가 정한다 — `publish()`가 `(SELECT event_seq FROM offices …)`로
채운다. **애플리케이션에서 계산해 넣지 마라.** 커밋 후 그 값을 읽어야 한다.

`worker/realtime/hub.ts`의 DO 자체는 건드리지 마라. 이미 검증됐다.

## 수용 기준

1. `npm run check` 통과 (**378개 이상.** 줄면 뭔가 깨진 것이다)
2. **`rg broadcastAfterCommit worker/`에 프로덕션 호출처가 있다** (테스트 외)
3. **실제 도메인 변경이 소켓에 도달한다** — 소켓을 열어두고 발송·상태변경·
   메모 추가를 각각 해서 프레임을 받아라. 테스트에서 `broadcast()`를 직접
   부르는 것으로 대신하지 마라
4. **MO 웹훅 수신이 소켓에 도달한다**
5. 프레임의 `officeSeq`가 **`GET /api/events`의 값과 같다**
6. **커밋 실패 시 방송이 안 나간다** — batch를 일부러 실패시켜 확인해라
7. **0행 변경(멱등 재시도·403) 시 방송이 없다**
8. **방송이 실패해도 응답이 정상이고 D1 이벤트 행이 남는다**
9. 방송이 응답 시간을 늦추지 않는다
10. 봉투가 캐치업 응답과 **글자 그대로 같다**
