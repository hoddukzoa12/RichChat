## 목표

첨부파일의 **기반**을 만든다 — 스키마, R2 바인딩, 공용 타입.
실제 수신·발송·렌더링은 다른 슬라이스가 한다. **여기서 만들지 마라.**

## 왜 필요한가

세무사무소에서 첨부는 부차적인 게 아니라 업무의 본체다. 고객은 사업자등록증
사본·영수증 사진·통장 사본을 보내고, 사무소는 확인서를 보낸다. 지금 설계에
이게 통째로 빠져 있었다 — 고객이 사진을 보내도 상담원 화면에 아무것도 안 뜬다.

사무소 설정에 **대화 보존 기간 5년**이 있다. 첨부를 저장하지 않으면 그 5년이
텍스트만 보존하는 셈이 된다.

## 만들 것

### 1. `migrations/0002_attachments.sql`

`0001_init.sql`은 **건드리지 마라.** 이미 리뷰를 거쳐 확정됐다. 새 마이그레이션을
추가한다. DB가 비어 있어 파일이 둘로 나뉘어도 문제없다.

`message_attachments` 테이블. 메시지 하나에 첨부 N개.

담아야 할 것:
- 자체 id (ULID). **배열 인덱스로 다루지 않는다**
- 어느 메시지의 것인지 (`messages`를 참조, 메시지 삭제 시 CASCADE)
- **테넌시** — `0001_init.sql`이 복합 FK로 사무소를 묶는 패턴을 쓰고 있다.
  **같은 패턴을 따라라.** 첨부가 다른 사무소 메시지에 붙는 일이 없어야 한다
- 원본 파일명, 바이트 크기, 확장자 또는 MIME 타입
- **R2 객체 키** — 우리가 저장한 위치. 아직 못 받았으면 비어 있다
- **다운로드 상태** — 아래 "수신 첨부의 수명" 참조. 이게 이 테이블의 핵심이다
- 수신/발송 구분이 필요한지는 네가 판단해라 (`messages.direction`으로
  파생되면 저장하지 마라 — SSOT)
- 생성 시각 (epoch 밀리초 정수)

**LGU+의 `contentUrl`을 서빙 경로로 저장하지 마라.** 일회성이고 24시간짜리다
(아래 참조). 감사 목적으로 남기고 싶으면 남기되, **화면이 그 URL을 가리키게
해서는 안 된다.** 진실은 R2에 있다.

`0001_init.sql`의 규칙을 그대로 따른다: `STRICT`, 시각은 정수, 파생값 저장 금지.

### 2. R2 바인딩 — `wrangler.jsonc`

버킷은 **이미 생성돼 있다.**

```jsonc
"r2_buckets": [
  { "binding": "ATTACHMENTS", "bucket_name": "richchat-attachments" }
]
```

바인딩 이름은 `ATTACHMENTS`다. wrangler가 제안하는 이름을 쓰지 마라.
`npm run types`로 `worker-configuration.d.ts`를 재생성해 커밋에 포함해라 —
`types:check`가 `npm run check`에 물려 있어서 안 하면 게이트가 막는다.

`wrangler.jsonc`의 **다른 필드는 건드리지 마라.**

### 3. 공용 타입 — `shared/`

첨부의 wire 타입을 `shared/wire/message.ts`에 넣는다. 지금은 스텁이다.

MIME 타입이나 첨부 종류를 유니온으로 둘 거면 `shared/domain.ts`의
기존 패턴(상수 배열이 원본, 타입은 거기서 파생)을 따라라.

## 알아야 할 외부 제약 — 스키마 설계의 근거다

**발송(MMS)** — 나중 슬라이스가 쓸 값이지만 스키마가 이걸 담을 수 있어야 한다.

제약이 **두 문서에 흩어져 있다.** 값을 의심하게 되면 여기를 봐라:

- `02 메시지발송 > 2.2 문자 메시지(SMS/MMS)` — 개수와 업로드 방식.
  "첨부파일은 3개까지 발송 가능", "사전에 업로드된 파일만 사용 가능".
  **여기에는 크기·형식 제한이 없다**
- `03 채널 > 3.2 컨텐츠(이미지) 관리` — 형식·크기·해상도. 채널별로 절이 나뉘어
  있고 **MMS 절**을 봐야 한다 (RCS·브랜드톡·푸시는 제한이 다르다)

MMS 기준:

- 형식: **JPG · JPEG · GIF만** (GIF는 첫 프레임만). **PDF는 보낼 수 없다**
- 크기: **최대 300KB**
- 해상도: 최대 1500×1440px
- 메시지당 최대 3개
- 업로드는 `POST /file/v1/mms`, 호스트가 발송과 다르다 —
  `mnt-api.msghub-qa.uplus.co.kr` (세 번째 호스트다)
- 응답의 `fileId`는 **만료된다** (`fileExpDt`). 그러므로 `fileId`를 영구 저장하고
  재사용하는 설계는 틀렸다 — 저장하더라도 만료 시각과 함께 다뤄야 한다

**수신(MMS MO)** — 고객 휴대폰이 보낸 것이라 형식·크기를 우리가 통제하지 못한다.
LGU+가 `GET /mo/v1/file/{moKey}`로 실물을 주고, 우리는 그대로 R2에 넣는다.
발송 제약(300KB·JPG)을 **수신에 적용하지 마라** — 고객이 보낸 걸 거부하면 안 된다.

이 비대칭이 중요하다. 스키마는 **수신 쪽 자유도**를 담을 수 있어야 한다.

### 4. 첨부 서빙 — `worker/routes/attachments.ts`

**이미지는 채팅창에 바로 보여야 한다.** 다운로드 링크가 아니다. 상담원이
고객이 보낸 영수증·사업자등록증을 매번 내려받아 여는 건 실무에서 안 쓴다.

그러려면 브라우저가 `<img src="/api/attachments/{id}">` 로 부를 수 있어야 한다.

`GET /api/attachments/:id` 를 구현해라.

- **세션 인증 필수.** 동일 출처 `<img>` 요청에는 쿠키가 실려 온다
- **테넌시 확인** — 요청자의 사무소와 첨부가 속한 사무소가 같은지 반드시 본다.
  id만 알면 남의 사무소 파일이 열리는 일이 없어야 한다
- R2에서 꺼내 **저장된 MIME 타입 그대로** 스트리밍한다.
  `await response.arrayBuffer()` 같이 전부 메모리에 올리지 마라
- **인라인 표시와 다운로드 두 모드를 지원해야 한다.** 상담원은 사진을 화면에서
  바로 보기도 하고, 원본을 받아 고객 폴더에 보관하기도 한다. 세무 증빙이라
  둘 다 필요하다. 같은 라우트에 모드를 주는 방식(쿼리 파라미터 등)으로 하되
  구체적인 형태는 네가 정해라
  - 인라인: `Content-Disposition: inline`
  - 다운로드: `Content-Disposition: attachment` + **원본 파일명**

  **파일명이 함정이다.** 고객이 보낸 파일명은 한글일 수 있다
  (`사업자등록증.jpg`). `filename="사업자등록증.jpg"` 처럼 비ASCII를 그대로
  넣으면 브라우저에 따라 깨지거나 헤더가 거부된다. **RFC 5987의
  `filename*=UTF-8''<percent-encoded>` 형식**을 써야 한다. 구형 호환을 위해
  ASCII `filename=`을 함께 주는 것도 고려해라.
  한글 파일명으로 실제 다운로드해보고 이름이 온전한지 확인해라
- 아직 다운로드되지 않은 첨부(대기 상태)는 **404가 아니라 구분 가능한 응답**을
  줘라. 화면이 "로딩 중"과 "없음"을 구별해야 한다. 형태는 네가 정해라
- 캐시 헤더 — 첨부는 한 번 저장되면 안 바뀐다. 다만 **인증이 필요한 자원**이므로
  공개 캐시에 들어가면 안 된다. 적절한 헤더를 골라라

**R2 공개 URL을 절대 노출하지 마라.** 고객의 사업자등록증·통장 사본이 링크만
알면 열리는 상태가 된다. 세무 데이터다.

**이 라우트 모듈은 B0의 스텁 목록에 없다.** 새로 만들고 `worker/index.ts`에
연결해야 한다. `worker/index.ts`는 원래 B0 전용이지만 **이번만 예외로 네가
한 줄 추가한다.** 다른 필드나 라우트 순서는 건드리지 마라.

## 만들지 말 것

- MO 수신 처리, 파일 다운로드, R2 업로드 로직 — 수신 슬라이스 소유
- 발송 시 파일 업로드 — 발송 슬라이스 소유
- 이미지 렌더링, `＋ 파일` 버튼 — 프론트 슬라이스 소유
- `migrations/0001_init.sql` 수정
- 실제 파일을 R2에 넣어보는 것 이상의 동작 코드

## 수용 기준

1. `npm run check` 통과
2. `migrations/0002_attachments.sql`이 적용되고 `0001_init.sql`은 무변경
   (`git diff`로 증명)
3. 첨부 테이블이 `STRICT`이고 시각 컬럼이 `INTEGER`
4. **다른 사무소 메시지에 첨부를 붙이는 INSERT가 거부된다** — 실제로 실행해 확인
5. 메시지 삭제 시 첨부가 CASCADE로 함께 사라진다 — 실제로 실행해 확인
6. `wrangler.jsonc`에 `ATTACHMENTS` 바인딩이 있고 `worker-configuration.d.ts`에
   `ATTACHMENTS: R2Bucket`이 생성돼 있다
7. 위 4·5가 회귀 테스트로 고정됨

**서빙 엔드포인트**

8. 세션 없이 `GET /api/attachments/:id` → 401
9. **다른 사무소의 첨부 id로 요청 → 접근 불가.** 실제로 두 사무소를 만들어 확인해라
10. 인라인 모드가 저장된 MIME 타입으로 응답하고 `Content-Disposition: inline`
11. 다운로드 모드가 `Content-Disposition: attachment`이고 **한글 파일명이
    온전하다** — `사업자등록증.jpg` 같은 이름으로 실제 저장해보고 확인해라
12. 다운로드 대기 중인 첨부와 존재하지 않는 첨부의 응답이 **서로 구별된다**
13. 응답이 공개 캐시에 들어가지 않는다

설계가 이상하다고 판단되면 구현하지 말고 `ask`로 물어라.
