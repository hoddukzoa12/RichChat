## 역할

슬라이스 B4(세션 해석·인증 층)에 대한 **독립 리뷰**다. 너는 구현자가 아니다.

`git diff main..HEAD`가 리뷰 대상이다. 구현자가 무엇을 의도했는지는 알려주지
않는다 — 알면 그 틀에 갇혀서 놓친다.

**먼저 저장소 루트의 `AGENTS.md`를 읽어라.**

## 왜 이 리뷰가 중요한가

**이후 10개가 넘는 슬라이스가 이 층 위에 올라간다.** 목록·상세·메모·업무·발송·
이벤트가 전부 여기서 `userId`와 `officeId`를 꺼낸다. 여기가 틀리면 전부 틀린다.

그리고 이건 **인증**이다. 다른 결함은 데이터가 이상해지는 정도지만, 여기 구멍은
남의 세션으로 들어오거나 권한을 우회하는 것이다. 세무 데이터다.

## 배경 (판단에 필요한 최소한)

세무사무소 고객문의 인박스. 직원 여러 명이 하나의 인박스를 공유한다.
Cloudflare Workers + D1. 역할은 `관리자`·`세무사`·`상담 담당`이고
사무소 설정 접근은 관리자만이다.

OIDC 로그인 자체는 **다음 슬라이스**다. 여기는 세션 해석·검증과 개발용
로그인 경로다.

## 검증할 것 — 직접 실행해서 확인하라

`npm run check`가 통과한다는 보고를 믿지 마라. 직접 돌리고, 나아가
**테스트가 실제로 무엇을 증명하는지** 읽어라.

### 1. 세션 토큰

- 쿠키에 담기는 값과 DB에 저장되는 값이 **다른가.** DB에 원문이 있으면
  DB를 읽을 수 있는 사람이 세션을 그대로 훔친다
- 토큰이 **추측 불가능한가.** 엔트로피가 충분한지, 예측 가능한 소스
  (시각·순번·약한 난수)를 쓰지 않는지 봐라
- 쿠키 속성 — `HttpOnly`·`Secure`·`SameSite`·`Path`
- **세션 고정** — 로그인할 때마다 새 토큰이 나오는가

### 2. 검증 경로

각각 **실제로 요청을 보내** 확인해라:

- 쿠키 없음 → 거부
- **만료된 세션** → 거부. `expires_at`을 실제로 보는가, 아니면 존재만 확인하는가
- **`status`가 `'활성'`이 아닌 직원** (`'초대'`, `'비활성'`) → 거부.
  퇴사자 계정이 남아 있어도 못 들어와야 한다
- 존재하지 않는 세션 id → 거부
- 위조한 쿠키 값 → 거부

### 3. `isAdmin`과 권한

- `isAdmin`이 **`users.role`에서 파생되는가.** 저장돼 있거나 클라이언트가
  보낸 값을 쓰면 실패다
- 같은 사용자의 `role`을 DB에서 바꾸면 `/api/me`의 `isAdmin`도 바뀌는가
- `PATCH /api/me`로 **이메일이나 역할을 바꿀 수 있는가.** 있으면 권한 상승이다.
  요청 본문에 그 필드를 넣어 실제로 시도해봐라

### 4. 개발용 로그인 — 가장 위험한 지점

운영에 열려 있으면 **누구나 아무 계정으로 로그인**한다.

- 바인딩이 **없을 때** 닫히는가
- 값이 **빈 문자열**일 때 닫히는가
- `"TRUE"`, `"True"`, `"1"`, `"yes"`, `" true "`(공백) 각각에 대해 닫히는가
- 켜진 상태에서만 동작하는가
- **이 경로가 다른 인증 검사를 우회하지 않는가** — 예를 들어 비활성 계정으로
  세션을 만들 수 있는가

### 5. CSRF

- 비-GET 요청에 다른 출처의 `Origin` → 거부되는가
- **웹훅 경로가 이 검사에서 빠져 있는가.** LGU+는 외부에서 오므로 `Origin`이
  없거나 다르다. 막혀 있으면 수신이 통째로 죽는다
- `Origin`이 **아예 없는** 요청은 어떻게 되는가. 그게 의도된 동작인가

### 6. 그 밖에

- `last_seen_at` 갱신이 **매 요청마다 D1에 쓰지 않는가**
- 오류 응답이 **정보를 흘리지 않는가** — "그런 사용자 없음"과 "비밀번호 틀림"을
  구분해 알려주면 계정 열거가 된다
- 떠다니는 Promise, 모듈 전역에 요청 스코프 상태, 바인딩 타입 `any`
- 세션 조회가 요청당 몇 번인가 — 중복 조회가 있는가

## 보고

`worker_done`으로 보고한다. 항목마다 통과/실패와 근거(명령 + 실제 출력).
실패는 심각도와 파일·줄 번호까지. 각 실패에 **어떤 공격이나 사고로 이어지는지**
한 줄 적어라.

**테넌시(교차 사무소) 시나리오는 우선순위를 낮춰라.** 이건 사무소 하나짜리
사내 도구다. 그 시간을 위 1~5에 써라.

문제를 못 찾았으면 그렇게 보고해도 된다. 없는 문제를 만들지 마라.
