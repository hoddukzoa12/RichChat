## 목표

**이벤트 캐치업.** `GET /api/events?since=<officeSeq>`

브라우저가 놓친 변경을 따라잡는 경로다. **실시간의 정합성이 여기에 달려 있다** —
WebSocket(B21)은 나중에 붙고, 붙은 뒤에도 갭이 생기면 클라이언트는 항상 여기로
돌아온다.

지금 프론트엔드는 새 메시지를 3.5초 `setTimeout`으로 흉내낸다.

## 왜 연속 번호인가

`events.office_seq`는 **사무소 안에서 1씩 증가**한다. `seq`(전역
`AUTOINCREMENT`)와 다르다.

클라이언트는 `lastSeq`를 들고 있다가 받은 이벤트가 `lastSeq + 1`이면 적용하고,
아니면 **갭을 감지해** 여기로 따라잡는다. 전역 번호를 사무소로 거르면 구멍이
생겨 연속성 판정 자체가 불가능하다.

**그러니 이 API가 내리는 이벤트는 빈틈없이 연속이어야 한다.**

## 반드시 지킬 것

### 봉투는 하나다

WS 프레임과 이 API의 행이 **같은 타입**을 쓴다. 두 벌로 만들면 한쪽만 고쳐져
클라이언트가 경로에 따라 다르게 동작한다.

`shared/wire/`에 정의하고, B21이 그대로 쓸 수 있게 해라. `payload`는 D1에
JSON 문자열로 저장돼 있으니 파싱해서 내려라 — 이중 인코딩된 문자열을 넘기지 마라.

### 커서

`since`보다 **큰** `office_seq`를 오름차순으로 낸다. `since=0`이면 처음부터다.

한 번에 낼 개수에 상한을 두고, **더 있는지 여부와 다음 커서를 응답에 실어라.**
클라이언트가 "다 받았다"고 오판하면 영원히 낡은 화면을 본다.

`OFFSET`을 쓰지 마라. `ux_events_office_seq(office_id, office_seq)`가 이미 있다.

### 너무 오래된 커서는 410이다

보존 기간이 지나 잘려나간 구간을 요청하면 **조용히 최신부터 주면 안 된다** —
클라이언트는 놓친 걸 모른 채 계속 간다.

**410**을 내려 "전체 다시 받아라"를 명시해라. 판정 기준은 네가 정하되
**근거를 코드 주석에 남겨라.**

지금은 정리 작업이 없어서 실제로 잘리지 않는다. **그래도 경로는 만들어라** —
나중에 보존 정리가 생길 때 클라이언트가 이미 대응돼 있어야 한다.

### `since`가 미래일 때

클라이언트의 `lastSeq`가 서버보다 크면 **DB가 되돌려졌거나 다른 환경을 보고 있다.**
빈 배열로 조용히 넘기지 말고 410으로 재동기화시켜라.

### 스코프

`office_id`는 **세션에서** 온다. 쿼리로 받지 마라.

### 읽기 전용이다

이 엔드포인트는 **아무것도 쓰지 않는다.** `events`에 행을 만들지도, 커서를
서버에 저장하지도 마라. 커서는 클라이언트가 들고 있다.

### 이벤트를 새로 발행하지 마라

`publish()`(B3)는 **각 변경 슬라이스가 자기 batch에서** 호출한다. 여기는 읽기만
한다. 없는 이벤트가 보이면 그건 그 슬라이스의 결함이니 보고해라.

## 수용 기준

1. `npm run check` 통과
2. 쿠키 없이 호출 → 401
3. **`since=0` → `office_seq`가 1부터 빈틈없이 연속**이다. 구멍이 있으면 실패다
4. `since=N` → `N`보다 큰 것만, 오름차순
5. 상한을 넘는 이벤트가 있을 때 **더 있음 표시와 다음 커서**가 실린다.
   그 커서로 이어 받으면 **중복·누락 0**
6. 페이지 사이에 새 이벤트가 생겨도 어긋나지 않는다
7. **너무 오래된 커서 → 410** (테스트로 조건을 강제해 확인해라)
8. **`since`가 서버 최대값보다 큼 → 410** (빈 배열 아님)
9. `payload`가 파싱된 객체다. 이중 인코딩된 문자열이 아니다
10. 호출 전후로 **DB에 쓰기가 없다** — 행 수와 `offices.event_seq`가 그대로
11. `EXPLAIN QUERY PLAN`이 `ux_events_office_seq`를 쓴다
