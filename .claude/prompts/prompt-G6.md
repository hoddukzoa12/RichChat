## 목표

**업무폰 등록을 자동화한다.** 관리자가 화면에서 등록 코드를 받아 폰에 입력하면
나머지가 자동으로 이어진다. 그리고 **서명키를 계정 공통으로 배포**한다.

지금은 관리자가 Device ID를 앱에서 복사해 손으로 붙여넣고, 서명키도 폰마다
따로 넣어야 한다. 폰이 여러 대라 이 방식은 안 된다.

## 확인된 계약 — 내가 서버·앱 소스로 직접 확인했다

### 등록 코드 발급

```
GET  https://<게이트웨이>/api/mobile/v1/user/code
Authorization: Basic <게이트웨이 계정 자격>
→ { "code": "123456", "validUntil": "..." }
```

6자리, 기본 300초, **1회용**(등록 성공 시 삭제). 서버 `mobile.go:101`에 있다.

폰은 앱에서 **Sign in by Code**로 그 코드를 입력한다. 그때 폰만 아는 정보(기기명·
푸시 토큰·SIM)가 함께 올라가 **Device ID가 서버에서 생성된다.**

**워커가 Device ID를 미리 만들 수 없다.** 반드시 앱이 등록해야 한다.

### 기기 목록

```
GET  https://<게이트웨이>/api/3rdparty/v1/devices
```

### 계정 공통 서명키

```
PATCH https://<게이트웨이>/api/3rdparty/v1/settings
{ "webhooks": { "signing_key": "<32바이트 키>" } }
```

앱의 `SettingsUpdateWorker`가 주기적으로 `getSettings()`를 호출해 로컬에
덮어쓴다(`WebhooksSettings.import()`). **폰마다 키를 넣을 필요가 없어진다.**

## 인프라 전제 — 보고에 반드시 적어라

`/api/mobile/v1/*`는 공개돼 있지만 **`/api/3rdparty/v1/*`는 터널에서 차단돼 있다.**
워커가 기기 목록과 설정 PATCH를 부르려면 **Access로 보호된 경로**가 필요하다.

**네가 인프라를 바꿀 수는 없다.** 워커는 **게이트웨이 관리 API의 기준 주소를
설정에서 받도록** 만들고, 그 주소가 무엇이어야 하는지 보고에 적어라.
내가 사용자와 함께 터널을 구성한다.

## 만들 것

### ① 등록 코드 발급

관리자가 **사무소 설정 → 업무폰**에서 누르면 코드가 뜬다.

응답에 담을 것: **앱에 넣을 API URL · 6자리 코드 · 만료 시각**

**반드시 지킬 것**

- **관리자만** (`office:manage`)
- 게이트웨이 계정 자격은 **워커 시크릿**. D1에 넣지 마라
- **코드를 D1·KV·로그에 저장하지 마라.** 한 번 보여주고 끝이다
- 응답에 `Cache-Control: no-store`
- **발급 요청에 제한을 걸어라.** 무제한이면 코드를 긁어낼 수 있다.
  방식과 근거는 네가 정해라
- 감사 로그에는 **요청자·시각·결과만.** 코드 값은 남기지 마라

### ② 등록된 기기 감지

폰이 코드로 등록하면 게이트웨이에 새 Device ID가 생긴다.
**화면이 그것을 찾아 보여줘야** 한다 — 관리자가 앱에서 복사할 필요가 없다.

기기 목록을 조회해 **아직 `office_channels`에 없는 것**을 골라 보여주고,
**라벨과 전화번호만 입력받아** 등록을 끝낸다.

**D1에 저장할 것은 라벨·전화번호·Device ID·사용 여부·등록 시각뿐이다.**
계정 비밀번호나 기기 인증 토큰을 저장하지 마라.

### ③ 서명키를 업무폰 전체에 배포

워커 시크릿의 **공통 키를 게이트웨이 계정 설정에 밀어 넣는** 경로를 만든다.
관리자가 화면에서 실행한다.

**키를 새로 만들지 마라.** 워커 시크릿에 이미 있는 값을 그대로 보낸다.
그래야 키가 존재하는 곳이 **워커 시크릿과 게이트웨이 두 곳뿐**이다.

배포 후 **폰이 실제로 반영했는지는 즉시 알 수 없다** (주기 워커가 가져간다).
화면이 그 사실을 정직하게 말해야 한다.

### ④ 시크릿 형식 — 공통 키 지원

지금 `SMS_GATEWAY_SIGNING_KEYS`는 `{deviceId: key}` 맵이다.
공통 키로 가면 **폰마다 줄을 추가해야 해서 자동화가 무의미**해진다.

**공통 키를 기본으로 두고, 기기별로 덮어쓸 수 있게** 해라. 형식과 해석 순서는
네가 정하되 **`.dev.vars.example`에 명확히 적어라.**

**기존 형식이 계속 동작해야 한다.** 지금 운영 시크릿이 `{deviceId: key}`이고
그 폰으로 실제 수신이 되고 있다. **깨뜨리면 운영이 멈춘다.**

## 보안 — 감수하는 것을 기록해라

계정 공통 키는 **한 대가 털리면 전체 수신을 위조**할 수 있다. 사용자가 자동화를
위해 의식적으로 선택했다. **`.dev.vars.example`에 그 사실과 회전 절차를 적어라.**

`PRIVATE_TOKEN`을 워커에 주지 마라. 기기 등록은 코드로만 한다.

## 수용 기준

1. `npm run check` 통과
2. **관리자가 코드를 발급받는다.** 응답에 API URL·코드·만료가 있고
   `Cache-Control: no-store`가 붙는다
3. **비관리자는 403**이고 게이트웨이 호출이 일어나지 않는다
4. **코드가 D1에 저장되지 않는다** — 저장소를 조회해 확인해라
5. **로그에 코드 값이 없다**
6. 발급 제한이 동작한다 (반례를 실제로 실행해라)
7. **미등록 기기 목록이 보이고, 라벨·번호만으로 등록된다**
8. 이미 등록된 기기는 목록에 **다시 안 나온다**
9. **서명키 배포가 게이트웨이 설정을 갱신한다** (목 요청 본문으로 확인)
10. **기존 `{deviceId: key}` 시크릿이 그대로 동작한다** — 게이트웨이 수신
    테스트가 수정 없이 통과
11. 공통 키만 있을 때도 **모든 기기의 수신이 검증된다**
12. 기기별 덮어쓰기가 공통 키보다 우선한다
13. 게이트웨이가 오류를 주면 **사람이 읽을 수 있는 메시지**가 뜬다. 500이 아니다
14. `dead-exports.py` · `positional-consts.py` · `unwired-routes.py` 통과

커밋하고 `origin/hoddukzoa12/g6-phone-enrollment`에 푸시한 뒤 해시를 보고해라.
배포하지 마라.
