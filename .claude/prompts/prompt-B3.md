## 목표

이후 모든 슬라이스가 D1을 다룰 때 쓸 **공용 기반**을 만든다.
여기서 정하는 관용구가 20개 슬라이스에 복제되므로, 잘못 잡으면 전부 잘못된다.

`worker/db/` 와 `worker/lib/` 아래에만 만든다. 라우트는 건드리지 않는다.

## 배경

세무사무소 고객문의 인박스. **D1이 유일한 정본이고 원자성은 조율이 아니라
제약으로 얻는다.** D1은 단일 라이터라 쓰기 트랜잭션이 교차하지 않고,
`db.batch()`는 하나의 직렬화된 트랜잭션이다.

스키마는 이미 있다. `migrations/0001_init.sql`을 **먼저 읽어라.**

## 만들 것

### 1. ULID 생성 — `worker/lib/ids.ts`

모든 id는 ULID다. **시간순으로 정렬 가능해야 한다** — 커서 페이지네이션이
`(last_message_at, id)` 복합 키로 동작하기 때문이다. UUID v4를 쓰면 안 된다.

같은 밀리초에 여러 개를 만들 때도 단조 증가해야 한다. 그렇지 않으면
같은 순간에 들어온 메시지 둘의 순서가 뒤집힌다.

### 2. `publish()` — 이벤트 발행 · **이 슬라이스의 핵심**

`events` 테이블은 감사 로그이자 실시간의 진실 원본이다. 각 이벤트는
**사무소 내에서 연속된 번호**(`office_seq`)를 갖는다. 클라이언트는 이 번호가
불연속이면 "놓친 게 있다"고 판단해 HTTP로 따라잡는다.

번호는 `offices.event_seq`를 하이워터마크로 써서 매긴다:

```sql
UPDATE offices SET event_seq = event_seq + 1 WHERE id = ?;
INSERT INTO events (office_id, office_seq, ...)
VALUES (?, (SELECT event_seq FROM offices WHERE id = ?), ...);
```

**가장 중요한 설계 제약 — `publish()`는 자기 트랜잭션을 열면 안 된다.**

이벤트 행은 **그것을 유발한 변경과 같은 `batch()` 안에서** 써야 한다.
따로 쓰면 "메시지는 저장됐는데 이벤트가 없는" 상태나 그 반대가 생기고,
그러면 클라이언트가 영원히 낡은 화면을 본다.

그러니 `publish()`는 `await db.batch()`를 호출하는 함수가 **아니라**,
호출자의 batch에 이어붙일 **statement 배열을 반환하는** 형태여야 한다.
이름과 시그니처는 네가 정하되 이 성질을 반드시 지켜라. 잘못 만들면
20개 슬라이스가 전부 원자성을 잃는다.

### 3. D1 헬퍼 — `worker/db/d1.ts`

앞으로 반복될 관용구를 여기서 한 번만 정의한다:

- **`meta.changes` 판정.** 낙관적 잠금(`UPDATE ... WHERE version = ?`),
  권한 검사(`UPDATE ... WHERE author_id = ?`), 멱등 삽입
  (`ON CONFLICT DO NOTHING`) 전부 "몇 행이 바뀌었나"로 결과를 판단한다.
  0행이 실패인지 정상인지는 **호출자마다 다르므로** 헬퍼는 판단하지 말고
  사실만 전달해라.
- **batch 실행과 오류 처리.** 실패 시 전체가 롤백된다는 성질을 호출자가
  신뢰할 수 있어야 한다.

`INSERT OR IGNORE`를 쓰는 헬퍼는 만들지 마라 — NOT NULL·FK·CHECK 위반까지
삼켜서 고객 메시지를 조용히 버린다. 충돌 타깃을 명시한 `ON CONFLICT`만 쓴다.

### 4. 시각 — 필요할 때만

시각은 전부 epoch 밀리초 정수다. 테스트 가능하게 하려면 `Date.now()`를
주입받을 수 있어야 한다.

**다만 함수 하나짜리 파일을 만들지 마라** (`AGENTS.md` §3). 담을 게
`nowMs()` 하나뿐이면 `worker/db/d1.ts`나 호출부에 두고 파일을 새로 만들지 마라.
판단은 네가 해라.

**MO의 `moRecvDt`(KST `yyyyMMddHHmmss`) 파싱은 이 슬라이스가 아니다.**
수신 어댑터 슬라이스가 담당한다. 만들지 마라.

## 만들지 말 것

- **시드 데이터.** 빈 DB로 시작한다. 목 데이터를 SQL로 옮기지 마라 —
  `src/data/seed.ts`와 두 번째 진실이 된다. 개발용 데이터는 수신 웹훅으로 넣는다
- 라우트 핸들러, 도메인 로직 — 다른 슬라이스 소유다
- 실제 Cloudflare 리소스 생성이나 배포. 전부 `--local`이다

## 수용 기준

1. `npm run check` 통과
2. ULID 1000개 생성 → 중복 0건, **정렬 순서가 생성 순서와 일치**
3. 같은 밀리초에 여러 개 생성해도 단조 증가 (시각을 고정해 테스트)
4. **`publish()`가 자기 batch를 열지 않는다** — 호출자 batch에 합쳐지는 형태임을
   테스트로 증명해라. 예: 실패하는 statement와 함께 batch에 넣으면
   이벤트 행도 **롤백되어야** 한다
5. `publish()` 2회 → `office_seq`가 1, 2로 **연속**
6. 서로 다른 사무소의 `office_seq`가 서로 영향을 주지 않는다
7. `grep -rc "INSERT OR IGNORE" worker/` → 0
8. `migrations/` 아래 새 파일이 없다 (시드 금지 증명)
