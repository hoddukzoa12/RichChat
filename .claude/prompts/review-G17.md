# 리뷰 — 새 메시지 (G17)

`AGENTS.md`를 먼저 읽어라. 이 저장소의 코딩 원칙이 판단 기준이다.

## 대상

```sh
git diff $(git merge-base main origin/hoddukzoa12/g17-compose-new) origin/hoddukzoa12/g17-compose-new
```

브랜치를 체크아웃해 **직접 실행**해라. 구현자의 보고를 믿지 마라.
슬라이스 정본은 `.claude/prompts/prompt-G17.md`다 — 기준이 거기 있다.

## 반드시 볼 축

**반례를 직접 만들어 실행해라.** 이 저장소에서 테스트 전체가 통과하는데
결함이 살아 있던 경우가 열두 번 있었다.

### 대화 생성의 원자성 — 가장 위험하다

- find-or-create가 **정말 한 문장의 `ON CONFLICT`인가**, 조회-후-삽입인가.
  같은 번호로 **동시에 두 요청**을 보내 대화가 하나인지 확인해라
- 고객 생성도 마찬가지다 — 같은 새 번호 동시 요청이 **고객을 둘 만들지
  않는가.** `customers`의 유니크 제약이 무엇인지 스키마에서 확인하고,
  제약이 없다면 그게 높음이다
- **생성과 동시에 수신이 도착하면?** 같은 (고객×폰)의 인바운드 웹훅과 compose
  요청이 겹칠 때 대화가 갈라지지 않는가

### 빈 대화

- 메시지 0건 대화가 **목록에 보이는가.** 정렬키(`last_message_at`)가 어떻게
  채워지고, 다른 대화와의 정렬이 자연스러운가
- 빈 대화에 **첫 수신이 들어오면** 정렬키 후퇴 가드(`WHERE ?new >=
  last_message_at`)에 걸려 갱신이 막히지 않는가 — 초기값이 크게 잡혀 있으면
  그렇게 된다
- 빈 대화가 미리보기·읽음 카운트·실시간 브로드캐스트 경로에서 널 참조를
  일으키지 않는가

### 번호 정규화 SSOT

- `worker/lib/phone.ts`는 기존 파일이다. **두 번째 정규화 구현이 어디에도
  생기지 않았는지** 확인해라 (프론트에 별도 정규화가 있으면 그것도 위반이다 —
  표시용 포맷팅은 예외)
- `010-1234-5678` / `01012345678` / `+821012345678` 세 입력이 같은 고객이
  되는지 실행해라

### 권한·검증

- 비로그인 401, 형식이 아닌 번호의 오류가 사람이 읽을 수 있는가
- 비활성 폰·`device_id` 없는 채널(대표번호)로 생성을 시도하면 막히는가

### 기존 경로 회귀

- 수신으로 생기는 대화 경로(`hooks-*` → `inbound-message`)가 그대로인가 —
  이 슬라이스는 그 파일들을 건드리지 않았지만 **같은 유니크 제약을 공유**한다
- `conversations.ts` 목록·상세 쿼리 변경이 기존 대화 표시를 바꾸지 않았는가

### 우선순위를 내릴 것

**테넌시.** 사무소 하나짜리 도구다. 교차 사무소를 높음으로 올리지 마라.

## 리뷰 공통 규칙

**파일을 수정하지 마라. 커밋하지도 마라.** 고칠 것을 찾으면 어디를 어떻게
고칠지 적어라.

문제를 못 찾았으면 그렇게 보고해도 된다. 다만 "괜찮아 보인다"만 쓰지 마라 —
실행한 명령과 실제 출력을 남겨라.

판정 기준: 높음이 아니고 재현 가능성이 낮은 지적은 **통과 + 후속 분리**로
해라. 단 **대화·고객 중복 생성과 데이터 유실은 낮은 확률이어도 높음이다.**

`worker_done`으로 보고한다 — 항목마다 통과/실패/해당없음과 근거(명령+출력),
실패는 심각도·파일·줄 번호와 사고 시나리오 한 줄, 전체 판정.
