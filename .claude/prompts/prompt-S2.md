## 목표

**직원 관리를 서버에서 완성한다.** 화면은 다음 슬라이스가 한다.

관리자가 직원을 **초대·수정·비활성화**할 수 있어야 하고, 새로 생긴
`부관리자` 역할이 실제로 그 일을 할 수 있어야 한다.

## 지금 무엇이 틀렸는가

### ① 초대하면 이름 자리에 이메일이 들어간다 — 운영에서 실제로 발생

운영 DB의 실제 행이다:

```
email: jinukim123@richgroup.by-works.net
name:  jinukim123@richgroup.by-works.net   ← 이메일이 이름 자리에
title: 상담 담당                            ← 역할이 직함 자리에
role:  상담 담당
```

`worker/routes/office.ts`의 초대 INSERT에서 **바인딩 순서가 어긋나 있다.**
직접 읽고 확인해라. 사용자가 화면에서 이걸 보고 신고했다.

### ② `부관리자`가 아무것도 못 한다

`shared/permissions.ts`가 `부관리자`에게 `team:view`·`team:manage`를 주는데,
**런타임 코드가 `hasPermission`을 한 번도 호출하지 않는다.**

```sh
rg -n "hasPermission" --glob '!shared/permissions*' .   # 결과 0건
```

독립 리뷰가 실제 세션으로 확인한 결과:

- `GET /api/me` → `isAdmin: false`
- `POST /api/office/invites` → 403
- `GET /api/office/members` → 200이지만 **초대 상태 직원이 빠지고 `status`도 없다**

마지막 항목이 중요하다. **권한만 열어도 목록이 관리에 필요한 데이터를
안 준다.** 응답 모양까지 함께 고쳐야 한다.

### ③ 직함을 본인이 고친다

`PATCH /api/me`가 `title`을 받는다. 직함은 **관리자가 관리해야 한다** —
사용자 요구다. 본인은 이름만 바꾼다.

### ④ 초대 후 수정·삭제가 없다

초대한 뒤 이름·직함·역할을 고칠 방법이 없고, 내보낼 방법도 없다.

## 무엇을 만드나

### 초대 — 이름·직함·역할을 받는다

지금은 이메일과 역할만 받는다. **이름과 직함을 함께 받아라.**
역할은 **네 가지 전부** 지정 가능해야 한다 (`관리자` 포함).

`shared/wire/office.ts`의 `INVITE_ROLES`가 지금 `관리자`를 뺀다.
사용자 요구는 "초대할 때에도 관리자/부관리자/상담 담당/세무사 다 지정 가능"이다.
**그 상수의 존재 이유를 다시 판단해라** — 없애는 게 맞으면 없애라.

이름이 비면 무엇을 넣을지는 네가 정해라. **다만 이메일 전체를 이름으로 넣지
마라** — 그게 지금 결함이다.

### 멤버 수정

이름·직함·역할을 바꾼다. 낙관적 잠금이 필요한지 판단해라 —
이 저장소에 `version` 패턴이 이미 있다.

### 멤버 비활성화

**행을 지우지 마라.** `users.status`를 `비활성`으로 바꾼다.
메시지·메모·업무가 작성자를 참조하므로 지우면 이력이 무너진다.

되살리는 경로도 만들어라. 사람은 돌아온다.

### 권한을 실제로 연결

`hasPermission`을 라우트에서 호출해라. 관리자 문자열 비교를 찾아 바꿔라.

**`AGENTS.md`가 요구하는 대로 권한은 `WHERE` 절에서도 강제해라.**
이 저장소에 이미 그 패턴이 있다 (`ADMIN_EXISTS_SQL`). 403을 앱 코드에서만
판정하면 경합에서 새어 나간다.

### `/api/me`가 권한을 알려줘야 한다

지금 `isAdmin` 불리언 하나다. 역할이 넷이 되었으니 **화면이 무엇을 보여줄지
판단할 수 없다.** 다음 슬라이스가 이걸로 사이드바와 화면 접근을 가른다.

무엇을 어떤 모양으로 내릴지는 **네가 정해라.** 판단 기준:
**화면이 역할 문자열을 다시 해석하지 않아도 되는가.**
`isAdmin`을 유지할지 없앨지도 함께 판단하고, 없애면 쓰는 곳을 전부 고쳐라.

### 멤버 목록

`team:manage` 권한이 있으면 **초대·비활성 상태 직원도 보이고 `status`가
포함돼야 한다.** 없으면 지금처럼 활성만.

## 지켜야 할 것

### 마지막 관리자를 잃지 마라

관리자가 0명이 되는 변경을 거부해라 — 역할 변경으로도, 비활성화로도.
**한 문장으로 표현해서 제약이 막게 해라.** 읽고 나서 쓰면 두 관리자가 동시에
자기 역할을 바꿀 때 둘 다 통과한다.

### 자기 자신을 비활성화하지 못한다

실수로 자기를 잠그면 되돌릴 사람이 없다.

### 부관리자는 관리자를 건드리지 못한다

`shared/permissions.ts`에 `team:manage-administrator`·
`team:assign-administrator`가 이미 있다. **그것을 써라.**
부관리자가 관리자를 수정·비활성화하거나 누군가를 관리자로 만들 수 없다.

## 소유 파일

- `worker/routes/office.ts`
- `worker/routes/me.ts` (`title` 제거, 권한 응답)
- `shared/wire/office.ts`, `shared/wire/me.ts`
- 위 파일들의 테스트

**화면(`src/`)은 다음 슬라이스다.** 다만 타입이 바뀌어 **컴파일이 깨지는 곳은
최소로 손봐라** — 동작을 옮기지 말고 컴파일만 되게. 무엇을 어디에 손댔는지
보고에 남겨라.

`migrations/`를 만들지 마라. 스키마는 이미 네 역할을 받는다.

## 수용 기준

1. `npm run check` 통과
2. **초대하면 `name`에 이름이, `title`에 직함이 들어간다** — 이메일이나 역할이
   아니다. 실제로 INSERT 하고 행을 읽어서 확인해라
3. 네 역할 전부 초대 가능
4. **부관리자 세션으로 직원을 초대할 수 있다** — 실제 세션을 만들어 호출해라
5. **부관리자가 받는 멤버 목록에 초대 상태 직원과 `status`가 있다**
6. 부관리자가 관리자를 수정·비활성화 → 거부. **그리고 행이 안 바뀐다**
7. 부관리자가 누군가를 관리자로 승격 → 거부
8. 상담 담당·세무사가 초대·수정 → 403, 행 불변
9. 마지막 관리자를 강등·비활성화 → 거부
10. 자기 자신 비활성화 → 거부
11. 비활성화는 **행을 지우지 않는다.** 그 사람이 쓴 메모·메시지가 남아 있다
12. 비활성 사용자의 기존 세션으로 API 호출 → 거부
13. `PATCH /api/me`에 `title`을 보내도 **직함이 안 바뀐다**
14. `rg "hasPermission"`이 `worker/`에서 **0건이 아니다**
15. `python3 .claude/scripts/dead-exports.py`에 `hasPermission`이 없다
