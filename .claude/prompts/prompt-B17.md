## 목표

**상담원이 고객에게 답장을 보낸다.** `POST /api/conversations/:id/messages`

인박스의 나머지 절반이다. B18이 받는 쪽을 만들었고 이게 보내는 쪽이다.

## 발송은 3단계다 — 어디서 죽어도 복구되게

LGU+ 호출은 **트랜잭션 밖**이다. 네트워크 호출을 트랜잭션 안에 넣을 수 없으므로
"보냈는데 기록이 없다"와 "기록은 있는데 안 보냈다" 중 **후자를 택한다.**

1. **batch** — `delivery_status='대기'`로 메시지 INSERT (+ 상태 전이 + 자동 배정 + 이벤트)
2. **LGU+ 호출** — 트랜잭션 밖
3. **batch** — `'접수'`로 전이 + `msg_key` 저장 + 이벤트. 실패면 `'실패'` + `error_text`

2와 3 사이에 isolate가 죽으면 `대기` 행이 남는다. **그건 정상이다** —
리포트 보정(B19)이 해결한다. 반대로 먼저 보내고 나중에 기록하면
고객은 답장을 받았는데 우리 화면엔 없다.

## 반드시 지킬 것

### 발송 멱등 — 클라이언트가 키를 만든다

`client_key`를 클라이언트가 만들어 보낸다(`messages.client_key`에 부분 유니크
인덱스가 있다). 같은 키로 두 번 오면 **메시지 1건, LGU+ 호출 1회**여야 한다.

네트워크가 끊겨 재시도할 때 고객에게 같은 문자가 두 번 가면 안 된다.

1단계에서 `ON CONFLICT(client_key) WHERE client_key IS NOT NULL DO NOTHING`.
`meta.changes === 0`이면 **이미 처리된 요청**이므로 기존 행을 반환하고
**LGU+를 호출하지 마라.**

`INSERT OR IGNORE`로 대체하지 마라.

### 바이트는 EUC-KR이다

`shared/sms.ts`의 `smsByteLength`·`pickMessageType`이 **유일한 구현**이다.
가져다 써라. **직접 세지 마라.**

`new TextEncoder().encode(s).length`는 **틀렸다** — UTF-8이라 한글이 3바이트다.
LGU+는 EUC-KR 기준으로 2바이트를 센다. `grep -c TextEncoder`가 이 슬라이스에서
0이어야 한다.

길이에 따라 SMS(90)↔LMS(2000)를 **자동 전환**하고, `TOO_LONG`이면 400이다.
이모지는 CP949에 없으므로 `containsEmoji`로 걸러라 — **정책은 네가 정하되
프론트엔드가 같은 판단을 할 수 있게 응답에서 이유가 분명해야 한다.**

### 자유 텍스트는 항상 SMS/LMS로 나간다

**알림톡은 사전 승인된 템플릿만 발송 가능하다.** 상담원이 입력한 자유 텍스트를
알림톡으로 보낼 수 없다.

그래서 `messages.channel`은 대화의 수신 채널과 무관하게 **`SMS` 또는 `LMS`**다.
원본 디자인과 달라지는 지점인데 **사실을 그대로 저장해라.** UI가 그대로 렌더한다.

### `callback`은 서버가 고른다

사무소의 `office_channels`에서 `kind='sms_callback' AND is_default=1 AND active=1`
인 발신번호를 쓴다.

**클라이언트가 보낸 발신번호는 절대 받지 마라.** 사전 등록된 번호만 쓸 수 있고,
클라이언트가 정하게 하면 남의 번호로 위장 발송이 된다.

기본 발신번호가 없으면 발송을 거부해라. 아무 번호나 고르지 마라.

### 상태 전이와 자동 배정

첫 응신에:
- `미처리` → `처리중`
- **미배정이면 발신자를 자동 배정**

둘 다 **1단계 batch 안에서** 한다. 이미 `처리중`이거나 이미 배정돼 있으면
그대로 둔다 (덮어쓰지 마라).

`완료` 대화에 답장하면 어떻게 할지는 **정해지지 않았다.** 판단이 필요하면
구현하지 말고 `ask`로 물어라.

### 정렬키

새 메시지가 대화의 `last_message_id`·`last_message_at`이 된다.
B18과 같은 **후퇴 방지 가드**를 걸어라 — `WHERE ?new >= last_message_at`.

### 토큰

`worker/lgu/token.ts`(B15)의 `getToken`을 써라. **재인증 로직을 다시 만들지 마라.**
`refresh` 엔드포인트는 절대 호출하지 마라 — 리프레시 토큰이 발급 IP에 묶여
있는데 Workers는 고정 egress IP가 없다.

### 첨부 — 사전 업로드

이미지를 함께 보낸다면 **발송 전에 컨텐츠 API로 올려** `fileIdLst`를 받는다.
**호스트가 발송과 다르다** (`LGU_CONTENT_HOST`).

발송 제약은 수신과 **비대칭**이다. 발송 MMS는 **JPG·JPEG·GIF만, 300KB,
1500×1440px, 3개까지**이고 **PDF는 안 된다.** 고객이 보낸 PDF를 되보낼 수 없다.

이 제약을 **수신에 적용하지 마라** — B18이 받은 것을 거부하게 된다.

첨부까지 이번에 할지 텍스트만 할지는 **네가 판단해라.** 미룬다면 그 사실을
보고에 명확히 적어라.

### 수신자 수와 응답 해석

요청당 수신자는 최대 10명이다. 여기는 1:1이라 항상 1명이지만 배열 형태다.

**200 응답은 *접수*일 뿐 도달이 아니다.** `완료`로 표시하지 마라 —
실제 도달은 리포트(B19)로 온다. 지금 프론트엔드가 "전송 완료"를 즉시 띄우는데
그게 결함이다.

## 수용 기준

1. `npm run check` 통과
2. 쿠키 없이 호출 → 401
3. **같은 `client_key` 2회 → 메시지 1건, LGU+ 호출 1회.**
   두 번째 응답도 성공이어야 한다 (에러 아님)
4. 45자 한글 → `SMS`, 46자 → `LMS`로 저장된다
5. 2000바이트 초과 → 400, **메시지 행이 안 생긴다**
6. `grep -c TextEncoder` = 0
7. **첫 응신 → `미처리`에서 `처리중`, 발신자가 자동 배정**
8. 이미 `처리중`이고 배정된 대화에 발송 → 담당자가 안 바뀐다
9. **클라이언트가 발신번호를 보내도 무시된다** — 실제로 본문에 넣어 시도해라
10. 기본 발신번호가 없으면 발송 거부
11. LGU+ 호출 실패 → `'실패'` + `error_text`, **행은 남는다**
12. LGU+ 호출 후 3단계 전에 죽은 상황 → `'대기'` 행이 남고 복구 가능
13. **성공 응답 후 상태가 `'접수'`다. `'완료'`가 아니다**
14. `last_message_at`이 후퇴하지 않는다
15. 발송 1건당 이벤트가 정확히 필요한 만큼
