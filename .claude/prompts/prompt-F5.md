## 지금 무엇이 틀렸는가 — 셋

### 1. 편집 시작 시 스냅샷을 뜨고 저장할 때 통째로 덮어쓴다

**두 사람이 같은 카드를 열면 나중에 저장한 쪽이 상대 수정을 조용히 지운다.**
세무 정보라 이게 실제 손해다.

서버가 `version`으로 낙관적 잠금을 건다. stale이면 **409 + `CONFLICT_VERSION`**과
함께 **현재 서버 값**을 돌려준다.

409를 받으면 **충돌 배너를 띄우고 사용자가 선택하게 해라.** 조용히 덮어쓰거나
조용히 버리지 마라 — 둘 다 사용자가 뭘 잃었는지 모른다.

### 2. 중첩 항목에 id가 없어 배열 인덱스로 갱신한다

메모·업무·커스텀 필드 전부. **상대가 항목을 하나 추가하면 인덱스가 밀려
엉뚱한 행이 수정되거나 지워진다.**

서버는 전부 id 기반이다. **인덱스로 지정하는 코드를 남기지 마라.**

### 3. 업무 상태가 왕복하면서 강등된다

편집기는 `warn`·`idle`·`done` 셋을 다루는데 저장 모델이 둘만 갖고 있었다.
`done`으로 저장 → 다시 열면 `idle` → 재저장하면 **완료한 부가세 신고가
대기로 강등된다.**

서버는 셋 다 저장한다. **편집기 값과 서버 값이 1:1로 일치하게** 해라.
중간에 매핑을 두면 같은 버그가 다시 난다.

**배지 문구(`D-3`·`대기`)는 `kind`에서 파생**한다. 저장하지도 받지도 마라.
`src/theme.ts`의 `Record` 패턴을 따라라.

## 반드시 지킬 것

### 메모 작성자는 id로 비교한다

`n.author === ME` 같은 이름 비교가 남아 있으면 **이름을 바꾸는 순간 자기 메모를
못 고친다.** 동명이인이면 남의 메모를 지울 수 있다.

서버가 `authorId`를 준다. 세션의 `userId`와 비교해라.

`customerCard.ts:244`의 `{ author: ME, ... }`가 사라진다 — **작성자는 서버가
세션에서 정한다.** 클라이언트가 보내지 마라.

### 낙관적 갱신과 `clientKey`

F1이 놓은 축대로 변경 요청에 `clientKey`를 싣는다. 서버 응답으로 임시 항목을
교체하되 **`clientKey` 먼저, 없으면 `id`**로 병합해라.

### 삭제는 서버가 소프트 삭제다

행이 남아 있고 조회에서만 빠진다. **클라이언트가 "지워졌다"고 믿고 로컬에서만
제거하지 마라** — 실패했는데 사라진 것처럼 보인다. 응답을 확인하고 반영해라.

### 상호와 직함

서버가 `company`와 `roleTitle`을 **따로** 준다. `orgLine.split(' · ')[0]`
같은 파싱이 남아 있으면 지워라 — 상호에 ` · `가 들어가면 잘린다.

입력도 둘로 나눠라. 표시용 결합은 렌더 시점에 한다.

### 전화번호

**여기서 바꿀 수 없다.** 그게 고객의 정체성이고 대화와 묶여 있다.
수정 UI를 만들지 마라. 마스킹은 표시 계층에서 한다.

## 수용 기준

1. `npm run check` 통과
2. **앱이 실제로 뜬다.** 카드를 열어 편집·저장해 확인해라
3. **stale `version` → 충돌 배너.** 두 탭을 열고 각각 저장해 실제로 재현해라.
   조용히 덮어쓰지 않는다
4. 메모·업무·필드가 **id로 갱신된다.** 항목 3개 중 가운데를 지운 뒤
   나머지를 수정해도 의도한 행이 바뀐다
5. **`kind: 'done'` 저장 → 다시 열기 → 재저장 → 여전히 `done`**
   (결함 #11의 직접 반례)
6. 배지 문구가 `kind`에서 파생된다. 저장·전송 0건
7. **메모 작성자 판정이 id 기반이다.** 프로필 이름을 바꿔도 자기 메모를
   계속 수정할 수 있다
8. 타인 메모 수정 시도 → 서버 403이 화면에 드러난다
9. 상호에 ` · `가 들어가도 온전하다
10. 상호·직함 입력이 둘로 나뉘어 있다
11. 전화번호 수정 UI가 없다
12. `grep -c 'ME' src/state/customerCard.ts` = 0
13. 삭제 실패 시 항목이 되돌아온다
