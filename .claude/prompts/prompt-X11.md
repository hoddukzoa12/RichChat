## 목표

**첨부를 실제로 받아온다.** 지금 6개가 전부 `대기`에 멈춰 있고 R2는 비어 있다.

수신 즉시 받고, 복수 첨부도 전부 받는다.

## 실측이 설계를 뒤집었다

내가 X4 프롬프트에 이렇게 썼는데 **세 가지가 다 틀렸다.**

> `contentUrl`은 일회성이고 24시간이다 → 재시도는 `GET /mo/v1/file/{moKey}`로 한다.
> **재시도 경로에 `contentUrl` 0건**

운영에서 실제로 확인한 것:

### ① `contentInfoLst`는 첨부마다 URL을 준다

```json
{"contentName":"FLMunz8ODc_0.jpg","contentSize":"288942","contentExt":"jpg",
 "contentUrl":"https://df25hb5tuwkue.cloudfront.net/mmsmo/null/null/2026/07/29/FLMunz8ODc_0.jpg"}
```

첨부 3개짜리 메시지는 **항목 3개, URL 3개**다. 매핑이 모호하지 않다.
지금 코드가 복수 첨부를 건너뛰는 이유가 사라졌다.

### ② `moKey` 재조회는 404다

```
GET /mo/v1/file/l0sSZPvGii.6gLlQs
→ 400 {"message":"기타 오류(404 NOT_FOUND)","code":"29003"}
```

첨부 1개·2개·3개 **전부** 같다. 보관 기한(7일)이 3시간밖에 안 지났으니
만료가 아니다. **이 경로는 동작하지 않는다.**

### ③ `contentUrl`은 일회성이 아니다

같은 URL을 두 번 불러 둘 다 `200`이었다. 바이트 수가 `contentSize`와 정확히
일치하고 JPEG 매직(`ffd8`)도 맞다.

**그리고 CloudFront 공개 URL이라 LGU+ 토큰도 IP 허용목록도 필요 없다.**

## 무엇을 만드나

### `contentUrl`을 저장한다

`message_attachments`에 컬럼을 더하는 마이그레이션이 필요하다.
**`migrations/0006_*.sql`을 새로 만들어라.** 기존 마이그레이션을 고치지 마라.

`0005`가 `users`를 재생성하며 겪은 함정이 있으니 **그 파일을 먼저 읽어라.**
컬럼 추가는 `ALTER TABLE ... ADD COLUMN`으로 되므로 재생성이 필요 없다.

만료 시각을 함께 둘지는 네가 판단해라. 문서는 24시간이라는데 반증하지 못했다
(3시간까지만 확인). **판단 근거를 보고에 적어라.**

### CloudFront에서 직접 받는다

토큰을 붙이지 마라. 인증이 없는 URL이다.

**호스트를 반드시 검증해라.** 이 URL은 외부 웹훅 페이로드에서 온다. 검증 없이
부르면 **공격자가 우리 워커로 임의의 주소를 호출하게 만들 수 있다.**
허용 호스트를 어떻게 정할지는 네가 판단해라 — 관측된 것은
`df25hb5tuwkue.cloudfront.net` 하나뿐이지만, 그것만 허용하면 LGU+가 CDN을
바꿀 때 조용히 전부 실패한다. **판단과 근거를 보고에 적어라.**

`https`가 아니면 거부해라.

### 수신 즉시 받는다

지금은 1분 cron이 주 경로다. 고객이 사업자등록증을 보내면 상담원 화면에
**"받는 중"이 1분 넘게** 떠 있다.

`worker/routes/hooks-mo.ts`가 이미 `ctx`를 받고 있고
`runAttachmentDownloads(env, options, ctx)`가 이미 export돼 있다.

**D1 커밋 후, `10000` 응답을 늦추지 않고** 다운로드를 시작해라.

`AGENTS.md`의 예외 조항에 정확히 해당한다:

> 응답 전에 미룰 수 있는 건 "무거운 작업"이 아니라 **"내구성과 무관한 작업"**뿐이다

다운로드는 내구성과 무관하다 — **cron이 안전망으로 남아 있기 때문이다.**
isolate가 죽어도 잃는 것이 없다.

**동기로 받지 마라.** 응답이 늦어지면 LGU+가 타임아웃하고 재전송한다.
**다운로드 실패가 `10000` 반환을 막아서도 안 된다.** 메시지는 이미 커밋됐다.

### cron은 보정용으로 남긴다

지우지 마라. 리포트와 같은 모양이 된다 — **웹훅이 주 경로, cron이 보정.**

### 복수 첨부 건너뛰기를 없앤다

`findAmbiguousMessages`와 그 경고 로그, 선점 쿼리의 `attachment_count = 1`
조건이 존재 이유를 잃었다. **걷어내라.**

`.claude/scripts/dead-exports.py`로 남는 죽은 코드가 없는지 확인해라.

## 밀린 6건

지금 `대기`인 6개는 **`contentUrl`이 저장돼 있지 않다.** 마이그레이션으로 컬럼을
만들어도 값이 없다.

이 슬라이스에서 되살리려 하지 마라 — 원본 페이로드가 저장소에 없다.
**내가 웹훅으로 다시 넣어서 처리하겠다.** 다만 같은 `mo_key`가 다시 들어와도
**메시지가 중복 생성되지 않아야** 한다. 그 멱등성이 유지되는지 테스트로 확인해라.

## 반드시 지킬 것

- **`contentUrl`을 브라우저에 내려보내지 마라.** 인증 없는 공개 주소다.
  고객 사업자등록증이 링크만 알면 열린다. 첨부는 지금처럼
  `/api/attachments/:id`로만 서빙한다. **응답 타입에 넣지 마라**
- R2에 실제로 객체가 올라가야 한다. **상태만 `완료`로 바꾸면 실패다**
- 리스·재시도·실패 확정 로직의 뼈대를 갈아엎지 마라
- 배포하지 마라

## 수용 기준

1. `npm run check` 통과
2. **첨부 3개짜리 메시지의 3개가 전부 받아진다** — `content_index` 0·1·2로
3. **R2에 객체가 실재한다.** 크기가 `contentSize`와 일치한다
4. 웹훅 응답이 **다운로드를 기다리지 않는다** — 응답 시간이 지금과 같다
5. **다운로드가 실패해도 `10000`을 반환한다.** 메시지는 저장돼 있다
6. **허용하지 않는 호스트의 URL은 받지 않는다** (반례를 실제로 넣어 확인)
7. `http://` URL은 거부한다
8. 다운로드 실패 후 **cron이 재시도한다**
9. 같은 `mo_key` 재전송 → 메시지 1건, 첨부 중복 없음
10. **응답 어디에도 `contentUrl`이 없다** — `grep`으로 확인
11. `python3 .claude/scripts/dead-exports.py`에 새 죽은 export가 없다

커밋하고 `origin/hoddukzoa12/x11-attachments`에 푸시한 뒤 해시를 보고해라.
