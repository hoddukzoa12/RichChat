## 역할

슬라이스 B2(D1 스키마)에 대한 **독립 리뷰**다. 너는 구현자가 아니다.
**파일을 수정하지 마라.**

이 워크트리에 B2 구현이 커밋돼 있다. `git diff main..HEAD`가 리뷰 대상이다.
구현자가 무엇을 의도했는지는 알려주지 않는다 — 알면 그 틀에 갇혀서 놓친다.

**먼저 저장소 루트의 `AGENTS.md`를 읽어라.** 위반이 있으면 그것도 findings다.

## 왜 이 리뷰가 중요한가

스키마는 **되돌리기가 가장 어렵다.** 코드는 즉시 롤백되지만 마이그레이션은 아니다.
그리고 이 프로젝트는 **원자성을 조율이 아니라 제약으로 얻는다** — 여기 제약이
하나 빠지면 앞으로 모든 동시성 보증이 근거를 잃는다. 응용 코드가 아무리 잘
짜여도 소용없다.

## 배경 (판단에 필요한 최소한)

세무사무소 고객문의 인박스. 고객이 문자로 보낸 문의가 외부 게이트웨이(LGU+)
웹훅으로 들어오고, 직원 여러 명이 하나의 인박스에서 공유하며 응대한다.
백엔드는 Cloudflare Workers + D1(SQLite). D1은 단일 라이터다.

## 반드시 검증할 것 — 각각 실제로 실행해서 확인하라

`npm run check`가 통과한다는 보고를 믿지 마라. **직접 돌리고**, 나아가
**테스트가 실제로 무엇을 증명하는지** 읽어라. 통과하는 테스트가 잘못된 것을
증명하고 있을 수 있다.

### 1. 제약이 실제로 막는가

각 제약에 대해 **위반하는 INSERT를 직접 실행**해서 거부되는지 봐라.
테스트가 있다고 넘어가지 말고 스스로 재현해라.

- 같은 `mo_key` 2회 INSERT → 두 번째가 0행 (수신 멱등)
- 같은 `client_key` 2회 → 두 번째가 0행 (발송 멱등)
- `direction='out'`인데 `sender_user_id`가 NULL → 거부
- `direction='in'`인데 `mo_key`가 NULL → 거부
- `direction='in'`인데 `delivery_status`가 `'완료'` → 거부
- 같은 사무소·같은 고객으로 대화 2개 → 거부
- 같은 사무소·같은 전화번호로 고객 2개 → 거부
- 같은 사무소에 `is_default=1`인 발신번호 2개 → 거부
- 같은 `(office_id, office_seq)` 이벤트 2개 → 거부

### 2. 부분 유니크 인덱스의 WHERE 절

`mo_key`·`client_key`·`msg_key`는 NULL이 많은 컬럼이다. `WHERE ... IS NOT NULL`이
빠지면 **NULL끼리 충돌하거나** 반대로 의도한 중복을 못 막는다. 각 인덱스의
WHERE 절을 확인하고, **NULL인 행을 여러 개 넣어봐서** 막히지 않는지 확인해라.

### 3. 파생값을 저장하고 있지 않은가

이 프로젝트는 파생 가능한 값을 저장하지 않는다. 단 **포인터는 저장하고 값은
조인한다** (`last_message_id`는 컬럼, 미리보기 텍스트는 조인).

- `badge` 같은 표시 문구 컬럼이 있는가 (있으면 위반 — `kind`에서 파생해야 한다)
- 이름 첫 글자(`initial`) 컬럼이 있는가 (위반)
- 미리보기 텍스트를 복제해 저장하는가 (위반)
- 반대로, 카운터(`inbound_count`)와 정렬키(`last_message_at`)는 **있어야 한다**

### 4. 시각이 정수인가

전부 `INTEGER` epoch 밀리초여야 한다. `TEXT`로 된 시각 컬럼이 하나라도 있으면
정렬이 깨진다. `PRAGMA table_info`로 실제 타입을 확인해라 — DDL 텍스트만 보지 마라.

### 5. STRICT

모든 테이블이 `STRICT`인가. `PRAGMA table_list`로 확인해라.

### 6. TS 유니온과 CHECK가 글자 그대로 일치하는가 ← 중요

`shared/domain.ts`에 도메인 유니온이 정의돼 있다. DB의 CHECK 제약과
**한 글자도 다르지 않아야** 한다. 다르면 런타임에 조용히 INSERT가 실패한다.
타입체커는 절대 못 잡는다.

`Status`·`Channel`·`Direction`·`DeliveryStatus`·`SendChannel`·`Role`·`UserStatus`
각각을 대조해라. 특히 `TaskKind`에 `'done'`이 있는지 — 이건 알려진 버그의 원인이었다.

### 7. 스키마에 없어야 할 것

- **세션 테이블이 있으면 안 된다.** 이 설계에서 대화가 곧 채팅방이고 상태는
  대화에 붙는다. `sessions` 테이블이 있으면 설계와 어긋난 것이다
  (단 로그인 세션 `auth_sessions`는 정상이다)
- AI·폴더 관련 테이블이 있으면 안 된다 (범위 밖)
- `users`에 `phone`이나 `signature` 컬럼이 있으면 안 된다

### 8. 그 밖에

- FK의 `ON DELETE` 동작이 합리적인가. 고객을 지우면 메시지가 남아 고아가 되는가
- 인덱스가 실제 조회 패턴을 받쳐주는가 (목록은 `office_id` + 최근순 + 보관여부로 뽑는다)
- `wrangler.jsonc`의 D1 바인딩이 `DB`이고 `database_id`가 플레이스홀더가 아닌가
- 마이그레이션이 재실행 가능한가, 아니면 최소한 실패가 명확한가

## 보고 방법

`worker_done`으로 보고한다. 항목마다 **통과/실패/해당없음**과 근거(실행한 명령과
실제 출력)를 붙인다. 실패는 심각도와 함께 파일·줄 번호까지 적어라.

**문제를 못 찾았으면 그렇게 보고해도 된다. 없는 문제를 만들어내지 마라.**
다만 "괜찮아 보인다"만 쓰지 말고 무엇을 어떻게 확인했는지를 남겨라.
특히 §1의 위반 INSERT를 직접 실행한 출력은 반드시 포함해라.

파일을 수정하지 말고, 커밋하지도 마라. 리뷰만 한다.
