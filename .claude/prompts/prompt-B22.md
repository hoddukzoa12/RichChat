## 업로드 계약 — 내가 운영 API로 직접 확인했다

**문서가 아니라 실측이다.** 그대로 구현해라.

```
POST https://{LGU_CONTENT_HOST}/file/v1/mms
Authorization: Bearer {토큰}
Content-Type: multipart/form-data

파트 둘:
  reqFile  = JSON **문자열** (파일이 아니다)
             { "fileId": "...", "wideYn": "N", "kkoItemListYn": "N",
               "kkoCarouselFeedYn": "N", "kkoCarouselCommerceYn": "N" }
  filePart = 실제 바이너리
```

성공 응답 (실측):

```json
{ "code": "10000", "message": "성공",
  "data": { "ch": "mms", "imgUrl": null, "imgUrlLst": null,
            "fileId": "probe_1785315598941",
            "fileExpDt": "2027-07-29T00:00:00" } }
```

관측한 오류:

| 코드 | 뜻 | 언제 |
|---|---|---|
| `21006` | 첨부파일 확장자 오류 | PNG를 올렸을 때 |
| `29001` | 필수 값 누락(reqFile) | reqFile 파트가 없을 때 |
| `29008` | 연동규격 오류 | filePart가 없을 때 |

**`fileId`는 우리가 정해서 보내고 서버가 그대로 돌려준다.**
**`imgUrl`은 `null`로 온다** — 문서 예시에는 값이 있지만 실제는 null이다.
**`fileExpDt`는 1년 뒤다.** 짧지 않다.

## 발송 계약 — 문서 기준, 미검증

```
fileIdLst: [ ... ]   최대 3개
title:     MMS 제목, 40 byte
```

### 경로를 바꾸지 마라 — 중요하다

문서는 `POST /xms/mms/v1`이라고 하는데, **우리 코드는 `/msg/v1/sms`·`/msg/v1/mms`를
쓰고 그게 실제로 동작한다.** 운영에서 `22002 미등록 발신번호`를 받았고, 그건
경로가 유효하다는 뜻이다(업무 레벨 응답).

API 계열이 두 벌인 것으로 보인다. **기존 경로를 유지하고 `fileIdLst`를 얹어라.**
LMS가 이미 `/msg/v1/mms`를 쓰므로 MMS도 같은 경로일 가능성이 크다.

**확신할 수 없다는 것을 코드 주석에 남겨라.** 발신번호가 등록되면 내가
실제로 확인하고, 다르면 그때 고친다.

## 무엇을 만드나

### ① 업로드 어댑터

`worker/lgu/` 아래. 바이트와 `fileId`를 받아 LGU+에 올린다.

**`worker/lgu/access.ts`의 공통 fetch를 지나야 한다** — Access 토큰 헤더가
붙어야 터널을 통과한다. 지나지 않으면 403이 난다.

**전역 `fetch`를 객체 속성으로 담았다가 호출하지 마라.** 오늘 그것 때문에
운영에서 100% 실패했다(`Illegal invocation`). 맨 호출로 써라.

### ② 브라우저가 이미지를 올릴 경로

화면이 고른 이미지를 서버로 보내는 길이 필요하다. **경로와 모양은 네가
설계해라.** 요구는 이렇다:

- **서버에서도 검증해라.** 화면 검증은 UX일 뿐 보안이 아니다.
  JPG/JPEG/GIF만, 300KB 이하, 최대 3장
- **R2에 저장해라.** 발신한 이미지도 나중에 스레드에서 보여야 한다
- **`fileId`로 우리 식별자를 써라.** 재시도해도 같은 id면 LGU+에 중복이
  안 생긴다. 이 저장소가 `client_key`로 발송 멱등성을 얻는 것과 같은 방식이다
- **클라이언트가 보낸 `fileId`를 믿지 마라**

### ③ 발송에 첨부를 싣는다

`MSG_ATTACHMENTS_UNSUPPORTED`를 걷어내고 실제로 보낸다.

- 첨부가 있으면 채널은 **MMS**다. `messages.channel` CHECK에 이미 있다
- **같은 `client_key`로 두 번 보내도 메시지 1건, LGU+ 호출 1회**여야 한다.
  기존 발송 멱등성이 첨부에도 적용되는지 확인해라
- `title`(40 byte)을 쓸지 판단해라. 컴포저에 제목 입력이 없다.
  **비우는 것과 본문에서 뽑는 것 중 무엇이 맞는지 정하고 근거를 적어라**
- **본문 없이 이미지만** 보낼 수 있는지도 정해라. 수신 쪽에는 본문이 `null`인
  사진 전용 MMS가 실제로 온다

### ④ 스레드 응답

발신 첨부가 **수신 첨부와 같은 모양으로** 내려가야 한다. 화면이 두 벌을
만들면 안 된다. `shared/wire/message.ts`의 기존 타입을 봐라.

## 지금 검증할 수 있는 것과 없는 것

- **업로드는 위 계약이 실측이다.** 목을 그 모양 그대로 만들어라
- **발송은 발신번호 미등록(`22002`)이라 끝까지 못 간다.**
  내가 등록 후 운영에서 확인한다

**목을 문서 모양으로 만들지 마라.** 오늘 이 저장소에서 문서와 실제가 어긋난
곳을 일곱 군데 찾았고, 전부 목이 문서의 사본이라 테스트가 통과하는데 운영이
죽었다.
