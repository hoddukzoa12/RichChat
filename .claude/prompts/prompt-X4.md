## 목표

**고객이 보낸 첨부의 바이너리를 실제로 가져와 R2에 넣는다.**

지금 수신 웹훅(B18)은 `message_attachments` 행을 `download_status='대기'`,
`r2_key=NULL`로 만들어 놓고 끝난다. **그 행을 소비하는 코드가 아무 데도 없다.**

메타데이터만 남고 바이트는 한 번도 저장되지 않는다. LGU+ 보관 기간 **7일**이
지나면 영구히 복구 불가능하다.

세무사무소에서 첨부는 부차적인 게 아니다 — 사업자등록증·영수증·통장 사본·
확인서가 업무의 본체다. 보존 기간 5년 설정이 있는데 첨부를 못 받으면
텍스트만 보존하는 셈이 된다.

**이건 구현자 잘못이 아니라 내 슬라이스 계획의 공백이었다.** 독립 리뷰가 잡았다.

## 반드시 지킬 것

### `contentUrl`을 재시도 정본으로 쓰지 마라

웹훅 페이로드의 `contentUrl`은 **일회성이고 24시간**이다. 저장해두고 나중에
쓰면 실패한다. B18이 저장하지 않은 것은 옳은 판단이다.

재시도는 **`GET /mo/v1/file/{moKey}`**로만 된다. 호스트는 `LGU_CONTENT_HOST`로,
발송·인증과 다르다. 보관은 **7일**이고 그게 복구 예산 전부다.

### 수신 응답을 늦추지 마라

**웹훅 핸들러를 건드리지 마라.** `hooks-mo.ts`는 B18 소유고, 이미
"메타데이터 동기 커밋, 바이너리는 미룸"으로 맞게 돼 있다.

여기는 **대기 행을 나중에 소비하는 쪽**이다.

### 무엇이 이 일을 깨우는가

`worker/scheduled.ts`의 Cron이 자연스러운 자리다. **Cron 최소 주기는 1분**이라
문서의 "10초 폴링"은 구현 불가능한데, 첨부는 그 지연이 문제되지 않는다.

`ctx.waitUntil`로 수신 직후에도 시도할지는 **네가 판단해라.** 다만 그건
**보조 경로일 뿐**이다 — isolate가 죽으면 사라지므로 Cron이 정본이어야 한다.
`waitUntil`만 두면 지금과 같은 유실이 다시 생긴다.

`worker/scheduled.ts`는 리포트 보정(B19)도 쓸 파일이다. **첨부 관련 함수만
추가하고 다른 스케줄 항목을 건드리지 마라.**

### 중복 다운로드를 막아라

Cron이 겹쳐 돌거나 여러 isolate가 같은 행을 집으면 같은 파일을 두 번 받는다.

**"읽고 나서 쓰기"를 한 문장으로** 표현해라. 조건부 UPDATE로 행을 선점하고
`meta.changes`로 획득 여부를 판정하는 방식이 D1에 맞는다
(`worker/lgu/token.ts`의 리스가 같은 발상이다).

**Durable Object를 쓰지 마라** — 정본을 갖는 순간 두 번째 진실이 생긴다.

### 상태 전이

`message_attachments.download_status`는 `대기`·`완료`·`실패`이고,
**`완료`면 `r2_key`가 있어야 한다는 CHECK가 이미 걸려 있다.**

- 성공 → `완료` + `r2_key`. **R2에 올린 뒤에** D1을 갱신해라.
  순서를 뒤집으면 `완료`인데 객체가 없는 상태가 생긴다
- 실패 → 재시도 가능하면 `대기` 유지, 시도 횟수·마지막 시각 기록
- **7일이 지나면 `실패`로 확정**해라. 영원히 재시도하면 매분 죽은 요청이 나간다

**실패도 두 종류다.** B18에서 이걸 안 갈라 리뷰가 [높음]을 냈다.

| 종류 | 예 | 처리 |
|---|---|---|
| 확정 | LGU+가 "그런 파일 없음"으로 응답 | 즉시 `실패`. 7일 기다리지 마라 |
| 일시적 | 타임아웃, 5xx, 토큰 만료 | `대기` 유지하고 재시도 |

일시적 오류로 `실패`를 찍으면 **아직 받을 수 있는 증빙을 스스로 포기**한다.
반대로 확정 부재를 7일간 재시도하면 매분 죽은 요청이 나간다.

전이는 **허용 선행 상태를 `WHERE`에 넣어** 단조롭게 만들어라.
이미 `완료`인 행이 다시 `대기`로 돌아가면 안 된다.

### R2 키

추측 불가능해야 한다. 고객 사업자등록증이 **키만 알면 열리면 안 된다.**
메시지 id나 첨부 id 같은 이미 있는 ULID를 쓰되, 공개 URL을 만들지 마라.

서빙은 `/api/attachments/:id`(X3 소유)가 세션 검사를 거쳐서 한다.
**여기서 서빙 경로를 만들지 마라.**

### 메모리에 통째로 올리지 마라

`await res.arrayBuffer()`로 전체를 올리면 큰 첨부에서 isolate가 죽는다.
스트림으로 R2에 넘겨라.

**수신에는 크기·형식 제한이 없다.** 발송 MMS의 제약(JPG만·300KB)을 여기
적용하지 마라 — 고객이 보낸 것을 거부하게 된다.

### 토큰

`worker/lgu/token.ts`(B15)의 `getToken`을 써라. 재인증 로직을 다시 만들지 말고
`refresh` 엔드포인트는 절대 호출하지 마라.

## 수용 기준

1. `npm run check` 통과
2. **대기 행이 실제로 소비된다** — 첨부가 있는 MO를 넣고 스케줄을 돌리면
   `download_status`가 `완료`가 되고 `r2_key`가 채워진다
3. **R2에 객체가 실제로 있다.** 상태만 바뀌고 객체가 없으면 실패다
4. `완료`인 행을 다시 돌려도 **재다운로드하지 않는다**
5. **동시에 두 번 돌려도 LGU+ 호출이 1회다** (선점이 실제로 되는지)
6. 다운로드 실패 → `대기` 유지, 재시도로 결국 성공한다
7. **7일 초과 → `실패`로 확정되고 더 이상 시도하지 않는다**
7b. LGU+가 "파일 없음"으로 확정 응답 → **즉시 `실패`** (7일 대기 안 함)
7c. 타임아웃·5xx → `대기` 유지. `실패`로 확정되지 않는다
8. `완료`인데 `r2_key`가 없는 상태가 만들어지지 않는다 (CHECK 위반이 아니라
   순서 자체가 그렇게 되지 않아야 한다)
9. `grep -c contentUrl` — 재시도 경로에서 0건
10. 큰 파일에서 전체를 메모리에 올리지 않는다
11. 웹훅 응답 시간이 늘지 않는다
12. `worker/routes/hooks-mo.ts`와 `worker/routes/attachments.ts`가
    **변경되지 않는다**

## 만들지 말 것

- 첨부 서빙(`/api/attachments/:id`) — X3 소유. 스텁 그대로 둬라
- MO 웹훅 수정 — B18 소유
- 발송 첨부 업로드 — B17 소유
- 리포트 보정 로직 — B19 소유. 같은 `scheduled.ts`를 쓰더라도 자기 함수만
- 프론트엔드(`src/`), `migrations/` 수정
