## 목표

**역할에 `부관리자`를 추가한다.** 스키마와 공용 타입만. API·화면은 다음 슬라이스다.

```
현재:  관리자 · 세무사 · 상담 담당
이후:  관리자 · 부관리자 · 세무사 · 상담 담당
```

## 가장 위험한 지점 — 되돌리기 어렵다

`users.role`에 `CHECK (role IN ('관리자','세무사','상담 담당'))`이 걸려 있고
**SQLite는 CHECK를 `ALTER`로 못 바꾼다.** 테이블 재생성이 필요하다.

그런데 `users`를 참조하는 **FK가 11개**다 — `auth_sessions`·`messages`(발신자)·
`notes`(작성자)·`tasks`·`conversation_assignees`·`conversation_reads`·
`office_settings`·`customer_fields`·`events`(액터) 등. `migrations/0001_init.sql`을
읽고 전부 확인해라.

**운영 D1에 이미 데이터가 있다.** 사무소 1개, 사용자 여러 명, 대화·메시지·이벤트.
마이그레이션이 데이터를 잃으면 복구 못 한다.

### 그래서

**재생성 없이 되는 방법이 있으면 그것을 택해라.** 예를 들어 CHECK를 지우고
애플리케이션·TS 유니온으로만 강제하는 방법도 있다 — 다만 그건 DB 보증을
포기하는 것이니 **택한다면 근거를 보고에 적어라.**

재생성으로 간다면:
- **외래키를 끈 상태에서** 복사·교체하고 다시 켜라
- 인덱스·제약·복합 FK 대상(`ux_users_id_office`)을 **전부 재생성**해라.
  하나라도 빠지면 다른 테이블의 복합 FK가 깨진다
- **로컬에서 실데이터를 넣고 적용해 행 수가 보존되는지 확인**해라

`migrations/0005_...`로 만들어라. **기존 마이그레이션을 수정하지 마라** —
이미 운영에 적용됐다.

## 공용 타입

`shared/domain.ts`의 `ROLES`에 `부관리자`를 넣어라.
**DB CHECK와 글자 그대로 일치**해야 한다 (`AGENTS.md` §언어).

순서도 의미가 있다 — 화면에서 이 순서로 나열된다. 권한이 높은 쪽부터가 자연스럽다.

## 권한 판정을 한 곳으로

지금은 `worker/routes/me.ts:237`의 `isAdmin: row.role === '관리자'` 하나뿐이다.
역할이 넷이 되면 **여러 곳에서 각자 비교하게 되고 그게 곧 두 번째 진실이다.**

권한을 묻는 **순수 함수를 `shared/`에 만들어라.** 예를 들어
"이 역할이 팀을 관리할 수 있는가", "사무소 설정을 바꿀 수 있는가" 같은 질문에
답하는 형태다. **정확한 모양은 네가 설계해라.**

확정된 권한 표는 이렇다:

| 동작 | 관리자 | 부관리자 | 세무사·상담 담당 |
|---|---|---|---|
| 팀 목록 조회 | ✓ | ✓ | ✓ |
| 초대·직함 수정·역할 수정·비활성화 | ✓ | ✓ | ✗ |
| **관리자를 대상으로 위 동작** | ✓ | **✗** | ✗ |
| **관리자 역할로 임명·초대** | ✓ | **✗** | ✗ |
| 사무소 설정(보존기간·내보내기) | ✓ | ✗ | ✗ |

**`isAdmin`은 그대로 두되** 의미가 흐려지지 않게 해라 — `/api/me` 응답 계약이고
프론트가 쓴다. 필요하면 값을 더하되 기존 것을 바꾸지 마라.

## 만들지 말 것

- 멤버 관리 API·초대 역할 지정·비활성화 — **다음 슬라이스**다.
  `worker/routes/office.ts`·`me.ts`를 고치지 마라
- 화면(`src/`) 수정

## 수용 기준

1. `npm run check` 통과 (398개 이상)
2. `migrations/0005_*`로 `부관리자`가 허용된다
3. **로컬에서 데이터를 넣고 마이그레이션을 적용해 행 수가 보존된다.**
   `users`뿐 아니라 이를 참조하는 테이블 전부 확인해라
4. 마이그레이션 후 **11개 FK가 여전히 동작한다** — 교차 위반 INSERT가 거부되는지
   실제로 시험해라
5. `ux_users_id_office` 등 인덱스가 남아 있다
6. `ROLES`가 DB CHECK와 **글자 그대로 일치**한다
7. 허용되지 않은 역할 문자열 INSERT → 거부(또는 CHECK를 뺐다면 그 근거와
   애플리케이션 방어를 보고에 명시)
8. 권한 함수가 위 표대로 답한다 — **네 역할 × 다섯 동작을 전부 테스트**해라
9. `/api/me`의 `isAdmin` 동작이 안 바뀐다
