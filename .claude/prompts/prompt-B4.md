## 목표

**세션에서 "지금 누가 요청했는가"를 알아내는 층**을 만든다.
이후 10개가 넘는 슬라이스가 여기 올라탄다 — 목록·상세·메모·업무·발송·이벤트 전부
`userId`와 `officeId`를 세션에서 꺼낸다. 여기가 틀리면 전부 틀린다.

OIDC 로그인 자체는 **다음 슬라이스**다. 여기서는 세션이 이미 있다고 가정한
**해석·검증 층**과, 개발용으로 세션을 만드는 경로를 만든다.

## 배경 — 지금 무엇이 틀렸는가

프론트엔드에 인증이 없고 이렇게 되어 있다:

```ts
// src/data/seed.ts
export const ME = '박상담'          // 모듈 상수
// src/state/inbox.ts
isAdmin: true,                      // 클라이언트 하드코딩
```

`ME`는 **표시 이름 문자열**인데 "내 담당" 필터·메모 작성자·메모 수정 권한 검사가
전부 여기 의존한다. 그런데 프로필의 이름은 따로 편집 가능하다 — **이름을 바꾸면
자기 담당 대화가 자기 필터에서 사라진다.**

`isAdmin`은 클라이언트가 정한다. 사무소 설정 페이지 접근과 정책 토글이
브라우저 판단에 달려 있다.

## 만들 것

### 1. 세션 해석 — `worker/http/session.ts`

요청에서 쿠키를 읽어 **누구인지 확정**한다. 결과에는 최소한
`userId`·`officeId`·`role`이 있어야 한다. 라우트 핸들러가 이걸 받아 쓴다.

**쿠키에는 불투명한 난수를 담고, DB에는 그 SHA-256만 저장한다.**
스키마의 `auth_sessions.id` 주석에 이미 적혀 있다 — 원문을 저장하면 DB를 읽을
수 있는 사람이 세션을 그대로 훔친다.

쿠키 속성: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`.

**만료된 세션은 거부한다.** `expires_at`을 실제로 확인해라.

`last_seen_at`은 매 요청마다 쓰지 마라 — API 호출 한 번마다 D1 쓰기가 생긴다.
갱신 주기를 정해서 그 안에서는 건너뛰어라. 판단은 네가 해라.

### 2. CSRF

`SameSite=Lax`만으로는 부족하다. **비-GET 요청에 `Origin` 검사**를 걸어라.
같은 출처가 아니면 거부한다. 웹훅 라우트(`/api/hooks/*`)는 외부에서 오므로
이 검사에서 빠져야 한다 — 어떻게 구분할지는 네가 정해라.

### 3. `/api/me` — `worker/routes/me.ts`

로그인한 직원의 정보를 돌려준다. 최소한 사용자(id·이름·직함·이메일·역할),
사무소, 개인 설정, 그리고 **`isAdmin`**.

**`isAdmin`은 `users.role`에서 파생한다.** 클라이언트가 보낸 값을 절대 믿지
않는다. 저장하지도 마라 — 역할에서 나오는 값이다.

`PATCH /api/me`로 프로필(이름·직함)을 고칠 수 있게 해라.
**이메일과 역할은 여기서 못 바꾼다** — 이메일은 OIDC가, 역할은 관리자가 정한다.

`PATCH /api/me/settings`로 알림 설정을 고친다.

### 4. 개발용 로그인 — `worker/routes/dev.ts`

OIDC 없이 세션을 만드는 경로. **이게 없으면 이후 슬라이스가 아무것도 테스트할 수
없다.**

**운영에서는 존재해서는 안 된다.** 실수로 남으면 누구나 아무 계정으로 로그인한다.
환경 변수로 막든 빌드에서 빼든 방법은 네가 고르되, **운영 설정에서 이 경로가
동작하지 않는 것을 테스트로 증명해라.**

사무소와 직원이 없으면 만들어야 세션을 붙일 수 있다. 개발용으로 최소한만
만들어라 — 목 데이터를 대량으로 넣지 마라. 대화나 메시지는 만들지 않는다
(그건 수신 웹훅으로 들어온다).

## 스키마 참고

`migrations/0001_init.sql`을 읽어라. `auth_sessions`·`users`·`offices`·
`user_settings`가 이미 있다. **마이그레이션을 수정하지 마라** — 필요하면
`ask`로 물어라.

`role`은 `'관리자' | '세무사' | '상담 담당'`, `status`는
`'초대' | '활성' | '비활성'`이다. **`status`가 `'활성'`이 아닌 직원은 로그인할 수
없어야 한다** — 초대만 받고 아직 수락 안 한 사람, 비활성화된 퇴사자가 여기 해당한다.

`worker/db/`의 헬퍼(`meta.changes` 조회, batch 실행)와 `worker/lib/ids.ts`의
ULID를 써라. 새로 만들지 마라.

## 수용 기준

1. `npm run check` 통과
2. 쿠키 없이 `/api/me` → 401
3. 만료된 세션 → 401
4. `status`가 `'활성'`이 아닌 직원의 세션 → 거부
5. **`auth_sessions.id`가 쿠키 원문이 아니다** — 저장된 값이 sha256 hex 64자이고
   쿠키 값과 다르다는 것을 테스트로 확인
6. **`isAdmin`이 `users.role`에서 나온다** — 같은 사용자의 role을 바꾸면
   `/api/me`의 `isAdmin`도 바뀐다
7. `PATCH /api/me`로 이메일이나 역할을 바꾸려 하면 무시되거나 거부된다
8. 비-GET 요청에 다른 출처의 `Origin` → 거부
9. **운영 설정에서 개발용 로그인이 동작하지 않는다** — 테스트로 증명
10. 쿠키에 `HttpOnly`·`Secure`·`SameSite=Lax`가 붙는다
