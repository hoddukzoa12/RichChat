## 목표

**발송한 문자가 실제로 도달했는지 확인한다.**

```
POST /api/hooks/lgu/report/:secret     ← 주 경로 (웹훅 푸시)
worker/scheduled.ts                     ← 보정 (Cron)
```

B17이 발송하면 상태가 `'접수'`에서 멈춘다. **200 응답은 접수일 뿐 도달이
아니다.** 실제 도달·실패는 리포트로 온다.

지금 프론트엔드가 발송 직후 "전송 완료"를 띄우는데 그게 결함이다.

## 상태 기계 — 허용 선행 상태가 곧 규칙이다

`대기 → 접수 → 전송중 → 완료 | 실패`

```sql
UPDATE messages SET delivery_status = '완료', result_code = ?, delivered_at = ?
 WHERE msg_key = ? AND delivery_status IN ('대기','접수','전송중')
```

**허용 선행 상태를 `WHERE`에 넣어 전이를 단조롭게 만들어라.**

이렇게 하면 두 가지가 공짜로 해결된다:

- **같은 리포트 재수신** → 이미 `완료`라 0행. 이벤트도 안 나간다
- **역순 도착** (`완료` 뒤에 늦은 `전송중`) → 0행. 완료가 뒤집히지 않는다

별도의 순위 컬럼이나 타임스탬프 비교를 만들지 마라. 상태 목록이 순서를 안다.

**`meta.changes === 1`일 때만 이벤트를 낸다.** `worker/db/events.ts`의
조건부 가드를 써라 — 그 파일을 읽어 현재 시그니처를 확인해라.

## 반드시 지킬 것

### 커밋 우선 — MO와 같은 규칙

**D1 커밋 후에만 성공 응답을 반환한다.** 먼저 ack하고 `waitUntil`로 미루면
isolate가 죽을 때 도달 상태를 잃는다. 그러면 그 메시지는 영원히 `접수`에
머문다.

### 실패를 두 종류로 갈라라

B18에서 이걸 안 갈라 리뷰가 [높음]을 냈다. 같은 함정이다.

| 종류 | 예 | 처리 |
|---|---|---|
| **결정적** — 페이로드 탓 | 필수 필드 누락, 알 수 없는 상태값, 형식 위반 | 로그 남기고 **200** |
| **일시적** — 인프라 탓 | D1 오류, 타임아웃 | **200이 아닌 코드.** 재전송 유도 |

일시적 오류에 200을 주면 **도달 정보를 영구히 잃고** 메시지가 `접수`에 박힌다.

**격리 테이블을 만들지 마라.** MO와 달리 리포트는 페이로드를 잃어도
Cron 보정이 상태를 결국 맞춘다 — 독립적인 복구 경로가 이미 있다.
결정적 항목에 200을 주는 것 자체가 무한 재전송을 막으므로 그것으로 충분하다.

**유효한 형제는 반드시 커밋해라.** 하나가 잘못됐다고 전체를 버리면 멀쩡한
도달 상태들이 같이 사라진다.

### 모르는 `msg_key`

리포트가 왔는데 그 `msg_key`의 메시지가 없을 수 있다 — 발송 3단계 중
②와 ③ 사이에 죽어 `msg_key`가 아직 저장 안 된 경우다.

**그걸 오류로 처리하지 마라.** 재전송을 유도해 나중에 결합되게 하거나,
보류 기록을 남겨라. 어느 쪽이든 **조용히 버리지 마라** — 그러면 그 메시지는
영원히 `접수`다.

판단이 필요하면 `ask`로 물어라.

### Cron은 보정이지 주 경로가 아니다

**Cron Trigger 최소 주기는 1분이다.** 문서의 "최소 10초 간격 폴링"은 Workers에서
구현 불가능하다. DO 알람 루프로 흉내내지 마라 — 복구 가능한 상태가 DO로
되돌아간다.

Cron은 **2분 이상 `대기`·`접수`·`전송중`에 머문 건**만 조회해 상태를 물어본다.
`ix_messages_pending` 인덱스가 그 조건으로 이미 있다.

**미결 건이 없으면 아무것도 하지 마라.** 매분 빈 요청을 보내지 마라.

`worker/scheduled.ts`의 **골격과 Cron 트리거는 X4(첨부 다운로드)가 만든다.**
네가 병합될 때 이미 있을 것이다.

**리포트 함수 하나를 추가하고 핸들러에 한 줄 끼워 넣는 것**이 네 범위다.
첨부 관련 함수와 `wrangler.jsonc`의 트리거 설정을 건드리지 마라.

파일이 아직 없으면 구현하지 말고 `ask`로 물어라 — 내가 순서를 잘못 잡은 것이다.

### 시크릿

`LGU_REPORT_WEBHOOK_SECRET`이 이미 선언돼 있다. **MO와 다른 값이다** —
하나가 새도 다른 하나는 살아 있어야 한다.

상수 시간 비교, 틀리면 404.

### 토큰

Cron 경로가 LGU+를 호출한다면 `worker/lgu/token.ts`의 `getToken`을 써라.
`refresh`는 절대 호출하지 마라.

## 수용 기준

1. `npm run check` 통과
2. **`완료` 뒤에 `전송중` 리포트 도착 → 상태 불변, 이벤트 0건**
3. **같은 리포트 2회 → 상태 1회만 바뀌고 이벤트 1건**
4. `접수` → `완료` 전이가 실제로 일어나고 `delivered_at`이 채워진다
5. 실패 리포트 → `'실패'` + `result_code`, `error_text`
6. D1 커밋 전에 성공 응답을 반환하는 경로가 없다
7. **일시적(D1) 실패 → 재전송 코드. 격리되지 않는다**
8. 결정적 실패 → 격리되고 나머지 트래픽은 흐른다
9. 잘못된 시크릿 → 404. **MO 시크릿으로는 통과하지 않는다**
10. 모르는 `msg_key` → 조용히 버려지지 않는다
11. **미결 건이 없으면 Cron이 외부 호출을 하지 않는다**
12. Cron이 2분 미만 건을 건드리지 않는다
13. `EXPLAIN QUERY PLAN`이 `ix_messages_pending`을 쓴다
