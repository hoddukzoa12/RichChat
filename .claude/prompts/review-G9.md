# 리뷰 — 업무폰 서명키 D1 이전 (G9)

`AGENTS.md`를 먼저 읽어라. 이 저장소의 코딩 원칙이 판단 기준이다.

## 대상

```sh
git diff main origin/hoddukzoa12/g9-signing-key-d1
```

브랜치를 체크아웃해 **직접 실행**해라. 구현자의 보고를 믿지 마라.

## 이 변경이 통과해야 하는 기준

1. 발급한 키로 서명한 **실제 `sms:received` 웹훅이 저장된다**
2. **다른 키로 서명하면 401**
3. **키를 발급하지 않은 기기의 웹훅은 401**
4. **재발급하면 이전 키가 즉시 401**
5. 발급 응답에 `Cache-Control: no-store`가 붙고 평문이 1회 나온다
6. **평문이 발급 응답 외에 어디에도 없다** — 폰 목록·상세·`events` payload·로그
7. 비관리자는 403이고 D1이 바뀌지 않는다
8. 마이그레이션이 **기존 데이터를 지우지 않는다**
9. `SMS_GATEWAY_SIGNING_KEYS`가 저장소 어디에도 남지 않는다
   (`.claude/prompts/`의 과거 문서는 예외)
10. `npm run check` 통과

## 반드시 볼 축

**반례를 직접 만들어 실행해라.** 통과하는 테스트가 무엇을 증명하는지 읽어라 —
이 저장소에서 테스트 10개가 전부 통과하는데 결함 3개가 살아 있던 적이 있다.

### 데이터 유실

- 마이그레이션 적용 전후로 `messages`·`conversations`·`office_channels` 행 수가
  같은가. **테이블을 재생성하지 않았는가** — 이 저장소는 `conversations`를
  재생성하면 `messages`의 `ON DELETE CASCADE`가 돌아 수신 이력이 사라진다
- 되돌릴 수 있는가. 컬럼 추가 외에 무엇을 바꿨는가

### 권한

- 세션 없음 / 비관리자 / 다른 사무소의 폰 id로 발급을 시도하면 어떻게 되는가
- 실패 경로에서 **D1이 정말 안 바뀌는가** — 행을 조회해 확인해라

### 키 노출

- 발급 응답 외의 모든 경로를 뒤져라. 목록·상세·`events.payload`·`console` 출력·
  프런트 상태·에러 메시지
- 브라우저에 남는가. 발급 후 다시 조회하면 무엇이 오는가

### 검증 경로

- HMAC 비교가 **상수 시간**인가
- 타임스탬프 창이 유지되는가
- `deviceId`가 없거나 빈 문자열일 때, 해당 행이 없을 때, `signing_key`가 NULL일 때
  각각 어떻게 되는가. **조용히 통과하는 경로가 있는가**

### 난수

- CSPRNG인가 (`crypto.getRandomValues`). `Math.random`이 쓰였으면 높음이다
- 길이가 충분한가

### 삭제가 남긴 구멍 — 특히 이것을 봐라

이 변경은 **테스트 파일 하나(288줄)를 통째로 지웠다.** 직전 커밋이 넣었던
검증이 함께 사라졌는지 확인해라.

```sh
git show main:worker/gateway/signing-keys.test.ts
```

거기서 검증하던 것 중 **지금 아무도 검증하지 않는 것**이 있는가.
특히 "실제 `sms:received`가 저장된다"와 "다른 키면 401"이 살아 있는가.

`vitest.config.ts`와 `src/theme.ts`도 바뀌었다. 이 둘은 구현자가 선언한 소유
범위 밖이다. **다른 테스트의 환경을 약하게 만들지 않았는지**, 화면에서 사라진
상태 값이 정말 도달 불가능한지 확인해라.

### 우선순위를 내릴 것

**테넌시.** 이건 사무소 하나짜리 사내 도구다. 교차 사무소 시나리오를 높음으로
올리지 마라. 그 비용을 위의 축에 써라.

## 리뷰 공통 규칙

### 너는 구현자가 아니다

**파일을 수정하지 마라. 커밋하지도 마라.** 리뷰만 한다.
고쳐야 할 것을 찾으면 고치지 말고 **어디를 어떻게 고쳐야 하는지 적어라.**

### 없는 문제를 만들지 마라

문제를 못 찾았으면 그렇게 보고해도 된다. 억지 지적을 만들면 진짜 지적이 묻힌다.

다만 **"괜찮아 보인다"만 쓰지 마라.** 무엇을 어떻게 확인했는지 —
실행한 명령과 실제 출력 — 을 남겨라. 그게 없으면 리뷰한 게 아니라 훑은 것이다.

### 보고 형식

`worker_done`으로 보고한다.

- 항목마다 **통과 / 실패 / 해당없음** 과 근거 (명령 + 실제 출력)
- 실패는 **심각도(높음/중간/낮음)와 파일·줄 번호**까지
- 각 실패에 **어떤 사고로 이어지는지** 한 줄
- 전체 판정: 통과 / 실패
