## 역할

슬라이스 B5(네이버웍스 OIDC 로그인)에 대한 **독립 리뷰**다. 너는 구현자가 아니다.

구현자가 무엇을 의도했는지는 알려주지 않는다 — 알면 그 틀에 갇혀서 놓친다.

**먼저 저장소 루트의 `AGENTS.md`를 읽어라.**

## 왜 이 리뷰가 중요한가

**이건 시스템에 사람이 들어오는 문이다.** 여기가 뚫리면 나머지 권한 검사는
전부 무의미하다 — 이미 안에 들어와 있기 때문이다.

세무 데이터다. 고객의 사업자등록증·매출·기장 내역이 들어 있다.

세션 **해석**은 다른 슬라이스(B4)가 이미 만들었고 리뷰도 통과했다.
여기는 세션을 **발급**하는 쪽이다.

## 배경 (판단에 필요한 최소한)

세무사무소 고객문의 인박스. 직원 여러 명이 하나의 인박스를 공유한다.
Cloudflare Workers + D1. 역할은 `관리자`·`세무사`·`상담 담당`.

**관리자가 초대한 이메일만 로그인할 수 있다.** 네이버웍스 인증에 성공했다는
것만으로 계정이 생기면 안 된다.

## 검증할 것 — 직접 실행해서 확인하라

`npm run check`가 통과한다는 보고를 믿지 마라. 직접 돌리고, 나아가
**테스트가 실제로 무엇을 증명하는지** 읽어라.

통과하는 테스트가 잘못된 것을 증명하고 있을 수 있다.

### 1. ID 토큰 검증 — 여기가 뚫리면 전부 끝이다

- **서명을 실제로 검증하는가.** 디코드만 하고 페이로드를 믿으면 누구나
  아무 이메일로 토큰을 만들어 로그인한다. **직접 위조 토큰을 만들어 던져봐라**
- `alg: "none"` 토큰을 거부하는가
- **대칭키 혼동** — `alg`를 `HS256`으로 바꾸고 공개키를 비밀키처럼 써서
  서명한 토큰을 거부하는가
- JWKS의 `kid`가 맞지 않는 토큰을 거부하는가
- `iss`·`aud`·`exp`를 각각 검사하는가. **하나씩 틀린 토큰을 만들어 확인해라**
- `exp`가 지난 토큰, `nbf`가 미래인 토큰
- **`nonce`를 저장만 하고 대조하지 않는가.** 대조 안 하면 재생 공격이 열린다

### 2. state와 PKCE

- **같은 state로 두 번 콜백**하면 두 번째가 거부되는가. 실제로 두 번 호출해라
- `DELETE … RETURNING`으로 소비하는가, 아니면 `SELECT` 후 `DELETE`인가.
  후자면 그 사이에 두 번 들어올 수 있다
- 만료된 state를 거부하는가
- state가 **추측 불가능**한가
- `code_verifier`가 실제로 토큰 교환에 쓰이는가

### 3. 초대 경계

- **미초대 이메일로 로그인 → 거부되고 `users` 행이 생기지 않는가.**
  DB를 직접 읽어 확인해라
- `status='비활성'`(퇴사자) → 거부되는가
- **응답이 초대 여부를 알려주는가.** 알려주면 계정 열거다
- 이메일 비교가 대소문자·공백에 안전한가. `Admin@x.com`과 `admin@x.com`
- **이메일 도메인만 보고 통과시키는 경로가 있는가**

### 4. 세션 발급

- **로그인할 때마다 새 토큰이 나오는가** (세션 고정)
- 쿠키에 담기는 값과 DB에 저장되는 값이 다른가
- 쿠키 속성 — `HttpOnly`·`Secure`·`SameSite`·`Path`
- **로그아웃이 DB 행을 지우는가.** 쿠키만 지우면 토큰이 계속 유효하다
- 발급된 세션이 `requireSession`으로 그대로 통과하는가

### 5. 열린 리다이렉트

`redirect_to`에 다음을 각각 넣어 **외부로 나가는지** 확인해라:

`//evil.com`, `https://evil.com`, `/\evil.com`, `http:/\/\evil.com`,
`javascript:alert(1)`, `/path?next=https://evil.com`

하나라도 나가면 피싱 경로다.

### 6. 시크릿과 노출

- 클라이언트 시크릿이 `vars`가 아니라 **secret 바인딩**인가
- 시크릿·토큰·`code`가 **로그나 오류 응답에 새는가**
- ID 토큰 원문이 어딘가 저장되는가
- 오류 화면이 내부 정보를 노출하는가

### 7. discovery와 JWKS

- discovery 문서를 받아 `issuer`·`jwks_uri`를 쓰는가, 아니면 경로를 조립해
  박아뒀는가
- **JWKS를 매 로그인마다 받는가** (성능) 또는 **영원히 캐시하는가** (키 롤오버 시 장애)
- discovery·JWKS 응답이 실패하면 어떻게 되는가. **실패가 로그인 성공으로
  번역되는 경로가 있는가**
- 외부 응답을 검증 없이 신뢰하는가

### 8. 테스트 자체를 의심해라

- **`vitest.config.ts`의 테스트용 바인딩을 지우면 테스트가 실패하는가.**
  값 없이도 통과한다면 그 테스트는 아무것도 증명하지 않는다
- 서명 검증 테스트가 **진짜 위조 토큰**을 쓰는가, 아니면 검증 함수를 목으로
  대체하는가. 목으로 대체했다면 서명 검증은 검증되지 않은 것이다
- 초대 경계 테스트가 DB 상태를 실제로 확인하는가

## 보고

`worker_done`으로 보고한다. 항목마다 통과/실패와 근거(명령 + 실제 출력).
실패는 심각도와 파일·줄 번호까지. 각 실패에 **어떤 공격으로 이어지는지**
한 줄 적어라.

**테넌시(교차 사무소) 시나리오는 우선순위를 낮춰라.** 사무소가 하나인
사내 도구다. 그 시간을 위 1~3에 써라.

문제를 못 찾았으면 그렇게 보고해도 된다. 없는 문제를 만들지 마라.
