## 목표

**`GET /api/events`의 410 응답에 현재 사무소 시퀀스를 실어준다.**

작은 슬라이스다. F7(실시간 구독)이 막혀 있다.

## 왜 필요한가

410은 "커서가 못 쓰게 됐으니 전부 다시 받아라"는 신호다. 클라이언트는
목록·스레드를 다시 불러온 뒤 **커서를 어디에 놓아야 하는지 알아야 한다.**

지금 410 본문에는 그 값이 없다:

```ts
function cursorGone(): Response {
  return error('GONE', '이벤트 커서가 현재 데이터와 맞지 않아 전체 동기화가 필요합니다.')
}
```

성공 응답에는 `nextCursor`가 있는데 410에만 없다. 그래서 클라이언트가
재동기화 후 **`since=0`으로 되돌아가거나(또 410이 날 수 있다) 아예 못 따라잡는다.**

## 무엇을 하나

410 응답에 **현재 사무소의 `office_seq` 최대값**을 실어라.
`offices.event_seq`가 그 하이워터마크다.

이벤트가 하나도 없는 사무소면 `0`이다 — 그 경우에도 값이 있어야 한다.

`shared/wire/event.ts`에 응답 타입을 정의해라. **F7이 그것을 import 한다.**
`EventCatchupResponse`를 건드리지 말고 새 타입을 더해라.

`worker/http/error.ts`의 `error()`가 상세를 실을 수 없으면 **그 파일에
추가하되 기존 항목을 건드리지 마라.** 여러 슬라이스가 공유한다.

## 반드시 지킬 것

**410을 내는 두 경로 모두**에 값이 실려야 한다 — 잘린 히스토리와
`since`가 서버보다 큰 경우. 한쪽만 고치면 나머지에서 클라이언트가 멈춘다.

**성공 경로의 동작을 바꾸지 마라.** `nextCursor`·`hasMore`·`events`가
지금 그대로여야 한다. F7이 이미 그 계약으로 구현 중이다.

값은 **읽기 전용으로 조회**해라. 이 엔드포인트는 아무것도 쓰지 않는다 —
`offices.event_seq`를 증가시키지 마라.

## 수용 기준

1. `npm run check` 통과 (**378개 그대로.** 줄면 뭔가 깨진 것이다)
2. **잘린 히스토리로 410 → 본문에 현재 시퀀스가 있다**
3. **`since`가 서버 최대값보다 큼 → 410, 본문에 현재 시퀀스가 있다**
4. 그 값이 실제 `offices.event_seq`와 같다
5. 이벤트가 없는 사무소 → 410일 때 `0`이 실린다
6. **성공 응답의 모양이 안 바뀐다** — `events`·`hasMore`·`nextCursor`
7. 호출 전후로 `offices.event_seq`가 불변이다
8. 타입이 `shared/wire/event.ts`에 있고 워커가 그것을 쓴다
