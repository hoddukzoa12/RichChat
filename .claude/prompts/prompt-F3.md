## 목표

**인박스 목록을 서버 데이터로 돌린다.** 지금은 모든 대화의 모든 메시지를
브라우저 메모리에 올려놓고 필터링·집계한다.

`src/state/selectors.ts`의 **다섯 함수만** 삭제하고 `GET /api/conversations`
(B6)의 응답을 그대로 쓴다.

같은 파일의 `assigneeLabel`(표시 문구), `answerFor`·`AI_SUGGESTIONS`(AI 탭)은
**그대로 둬라.** AI 탭 정리는 F8 소유고, 지금 지우면 그 화면이 죽는다.
파일을 통째로 지우지 마라.

## 지금 무엇이 틀렸는가

`src/state/selectors.ts`를 읽어라.

- `visibleList` — 보관·담당범위·상태·검색을 메모리에서 거른다
- `statusCounts` · `scopeCount` · `archivedCount` — 전수 순회
- `preview` — `c.messages[c.messages.length - 1]`.
  **목록을 그리려고 모든 대화의 전체 메시지 배열이 필요하다**

그리고 **칩 숫자와 목록이 어긋난다.** `statusCounts`는 보관함까지 세는데
`visibleList`는 보관을 제외한다. 서버가 이미 이걸 고쳐서 내려준다.

## 서버가 주는 것

`shared/wire/conversation.ts`의 `ConversationListResponse`를 **읽어라.**
타입을 새로 만들지 마라 — 이미 있다.

- `conversations[]` — 각 항목에 고객·미리보기·안읽음·담당자·상태·라벨·보관·`version`
- `nextCursor` — 다음 페이지
- `facets` — `status`·`scope`·`archive` 카운트

**패싯 계약을 이해하고 써라.** 상태·담당 카운트는 선택된 보관 값을 적용한
것이고, 보관 카운트만 자기 차원을 제외한다. 그래서 활성 뷰를 보는 중에도
"보관함 12"가 나온다. **클라이언트에서 다시 계산하지 마라.**

## 목표 상태 모양 — 디스패치 전에 내가 정한다

F3·F4·F5가 병렬로 돌기 때문에 **서로 다른 모양을 가정하면 병합에서 깨진다.**
아래를 전제로 구현해라.

### `src/state/conversations.ts`는 F3 소유다

시드(`CONVERSATIONS`)가 들어오는 자리이고 `patchSelectedConversation`을
셋이 공유한다. **F3만 수정한다.**

- `convs`는 **목록 항목**만 담는다 — 고객·미리보기·안읽음·담당자·상태·라벨·
  보관·`version`. 서버 `ConversationListItem` 그대로다
- **`convs[].messages`는 없어진다.** 목록 응답에 메시지가 없다
- **`convs[].notes`·`tasks`·커스텀 필드도 없어진다.** 상세 응답에만 있다

### 메시지와 상세는 별도 슬라이스 상태다

| 무엇 | 어디 | 소유 |
|---|---|---|
| 목록 항목 배열 | `conversations.ts`의 `convs` | **F3** |
| 열린 대화의 메시지 | 새 상태 (대화 id로 키) | **F4** |
| 열린 대화의 카드·메모·업무 | 새 상태 | **F5** |

**`currentConv().messages`를 읽는 코드는 사라진다.** F4가 자기 상태에서
가져온다. F5도 마찬가지다.

`inbox.ts`(조립점)에 새 슬라이스를 등록해야 하면 **그 한 줄만** 추가해라.
다른 줄을 건드리지 마라 — 셋이 같은 파일을 만진다.

### 왜 이렇게 가르나

목록은 **페이지네이션되고 자주 갱신**되지만 메시지·카드는 **열린 대화 하나만**
필요하다. 한 배열에 다 넣으면 목록을 새로 받을 때마다 열어둔 대화의
메시지가 날아가거나, 반대로 오래된 목록 항목이 남는다.

## 반드시 지킬 것

### 파생 계산을 클라이언트로 되돌리지 마라

서버가 준 `unreadCount`·`preview`·`facets`를 그대로 렌더해라.
**"혹시 몰라서" 다시 세는 코드를 넣지 마라** — 두 번째 진실이 된다.

목록 항목에 메시지 배열이 없다. 필요하면 상세 API(B7)를 호출한다.

### 커서 페이지네이션

`nextCursor`가 `null`이면 끝이다. 스크롤로 이어 받을 때 **이미 받은 항목을
다시 넣지 마라** — id로 병합해라.

`OFFSET`이나 페이지 번호를 만들지 마라.

### 검색 입력

타이핑마다 요청하지 마라. 디바운스를 걸되 **마지막 입력이 반드시 반영되게**
해라 — 중간 응답이 늦게 도착해 최신 검색어를 덮는 경합이 흔하다.

응답이 어느 요청의 것인지 식별해서 오래된 것을 버려라.

### `ME` 제거

`selectors.ts:17`의 `c.assignees.includes(ME)`가 사라진다. 담당 범위 필터는
**서버가 세션 사용자 기준으로** 계산해 내려준다. 쿼리로 `scope`만 보내라.

`ME` import를 지워라. `src/data/seed.ts`의 정의는 **F8이** 지운다.

### 로딩과 오류

첫 로딩, 추가 로딩, 빈 목록, 오류를 구분해 보여줘라.
**빈 목록과 로딩 중을 같게 그리지 마라** — 사용자가 "문의가 없다"고 오해한다.

오류를 조용히 삼키지 마라.

## 수용 기준

1. `npm run check` 통과
2. **앱이 실제로 뜬다.** `npm run dev`로 띄워 목록을 확인해라
3. **`selectors.ts`의 다섯 함수가 삭제된다** — `visibleList`·`statusCounts`·
   `scopeCount`·`archivedCount`·`preview`
4. 칩 숫자가 **서버 `facets`에서** 온다. 클라이언트 집계 0건
5. **칩을 누르면 그 숫자만큼 나온다** (지금 결함 #12의 직접 반례)
6. 활성 뷰에서도 보관함 칩에 숫자가 보인다
7. 안읽음이 서버 값이다. 클라이언트가 다시 세지 않는다
8. 미리보기가 서버 값이다. 메시지 배열을 참조하지 않는다
9. 스크롤로 두 페이지를 받아도 **중복 항목 0**
10. 검색어를 빠르게 바꿔도 **마지막 입력의 결과가 표시된다**
11. `grep -c 'ME' src/state/selectors.ts` = 0
12. 목록 렌더에 `conversation.messages` 참조가 없다
