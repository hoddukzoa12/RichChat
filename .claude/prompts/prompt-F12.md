## 목표

**소켓이 붙어 있을 때 폴링을 늦춘다.** `src/hooks/useRealtime.ts` 한 파일이다.

## 지금 무엇이 낭비인가

`src/hooks/useRealtime.ts:107`

```ts
export function pollingDelay(hidden: boolean): number {
  const visibility = hidden ? 'hidden' : 'visible'
  return POLL_INTERVAL_MS[visibility]   // visible 5초 / hidden 30초
}
```

**소켓 연결 상태를 보지 않는다.** WebSocket이 정상 연결돼 프레임을 받고 있어도
탭이 열려 있으면 5초마다 `GET /api/events`를 친다.

운영 실측(6시간):

```
GET /api/events   5,885건 · CPU 7,428ms   ← 전체 fetch 요청의 82%
그 외 API 전부      1,295건
GET /api/realtime    137건               ← 소켓은 실제로 붙어 있다
```

**같은 일을 두 경로가 동시에 하고 있다.**

원인은 설계 순서다. 계획서가 "폴링을 먼저 띄우고 WebSocket을 나중에 끼워
넣는다"고 정했는데(정합 로직을 먼저 증명하려는 의도, 그건 옳았다),
**소켓이 들어온 뒤 폴링을 늦추는 슬라이스를 만들지 않았다.**

## 무엇을 하나

**소켓이 건강할 때 폴링을 안전망 수준으로 늦춰라.** 끊기면 지금 간격으로 돌아온다.

간격 값은 네가 정해라. 판단 기준:

- 소켓이 프레임을 흘렸을 때 **얼마나 늦게 알아차려도 되는가**
- 소켓이 죽었는데 `close` 이벤트가 안 온 경우 **얼마 만에 복구되는가**

지금 값(5초/30초)이 왜 그 숫자인지도 보고, 바꾸는 값의 근거를 보고에 적어라.

### 폴링을 없애지 마라

폴링은 **소켓이 조용히 프레임을 흘렸을 때의 안전망**이다. 계획서가 그렇게
설계했고 실제로 그 상황이 존재한다(isolate 축출, 버퍼 포화, 재접속 중).

**소켓이 붙어 있어도 폴링은 계속 돌아야 한다.** 간격만 늘린다.

## 깨뜨리면 안 되는 것

이것들은 **주기가 아니라 이벤트로 도는** 경로다. 그대로여야 한다.

- **갭 감지 캐치업** — `officeSeq`가 불연속이면 즉시 따라잡는다
- **재접속 캐치업** — 소켓이 다시 붙으면 먼저 캐치업한다
- **탭 복귀 캐치업** — `visibilitychange`
- **커서 만료(410) 처리**

소켓 상태가 바뀌는 순간 **다음 폴링을 기다리지 말고 간격을 즉시 반영**해라.
소켓이 끊겼는데 60초를 기다리면 그동안 아무것도 못 받는다.

## 기존 테스트

`src/hooks/useRealtime.test.ts:123-124`가 `pollingDelay`를 직접 부른다.

```ts
expect(pollingDelay(false)).toBe(5_000)
expect(pollingDelay(true)).toBe(30_000)
```

시그니처를 바꾸면 여기도 고쳐야 한다. **테스트가 무엇을 증명하려던 것인지
읽고, 그 의도를 유지한 채 새 축을 더해라.** 숫자만 바꿔 통과시키지 마라.

## 수용 기준

1. `npm run check` 통과
2. **소켓이 연결된 상태에서 폴링 간격이 늘어난다**
3. **소켓이 끊기면 짧은 간격으로 돌아온다** — 다음 주기를 기다리지 않고
4. 탭을 숨기면 여전히 더 늦어진다
5. **갭 감지 캐치업이 그대로 동작한다** — 불연속 `officeSeq`를 주고 확인해라
6. **재접속 시 캐치업이 그대로 동작한다**
7. 기존 테스트의 **의도**가 유지된다 (숫자만 맞춘 것이 아니어야 한다)
8. 앱이 실제로 뜬다

## 참고

이 저장소는 목이 실제와 다를 수 있다는 것을 오늘 여섯 번 겪었다.
**타이머 테스트는 가짜 타이머로 쓰되, 소켓 상태 전이를 실제로 일으켜서**
간격이 바뀌는지 확인해라. 상수를 직접 읽어 비교하는 테스트는 배선을 증명하지
못한다.
