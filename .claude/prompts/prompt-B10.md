## 목표

고객 카드 수정. `PATCH /api/customers/:id`

이름·상호·직함과 **커스텀 필드**(사업자번호·업종·기장료 같은 임의 항목)를 고친다.

## 지금 무엇이 틀렸는가

프론트엔드는 편집을 시작할 때 카드 전체를 스냅샷으로 뜨고, 저장할 때 그걸
통째로 덮어쓴다. **두 사람이 같은 카드를 열면 나중에 저장한 쪽이 상대 수정을
조용히 지운다.** 세무 정보라 이게 실제 손해다.

그리고 커스텀 필드에 **id가 없어서** 배열 인덱스로 갱신한다. 상대가 필드를
하나 추가하면 그 뒤 항목이 전부 밀려 **엉뚱한 값이 덮인다.**

## 반드시 지킬 것

### 낙관적 잠금

`customers.version`을 받아서 조건에 건다.

```sql
UPDATE customers SET name = ?, ..., version = version + 1, updated_at = ?
 WHERE id = ? AND version = ?
```

`meta.changes === 0` → **409**. 응답에 현재 서버 값 전체를 실어 클라이언트가
충돌 화면을 그릴 수 있게 해라.

**409일 때 아무것도 안 바뀌어야 한다.** 고객 본체는 실패했는데 필드는 들어가는
부분 적용이 생기면 안 된다 — 같은 batch에 넣고, **필드 변경도 `version` 조건에
묶어라.**

### 커스텀 필드는 id로 갱신한다

`customer_fields`에 `id`(ULID)가 이미 있다. **배열 인덱스나 순번으로 찾지 마라.**

- 추가 → 새 id 발급
- 수정 → id로 지정
- 삭제 → id로 지정
- 순서 변경 → `sort_order` 갱신

`ux_fields_key(customer_id, key)`가 있어 같은 키 중복은 DB가 막는다. 그 실패를
500으로 흘리지 말고 **409나 400으로 번역**해라.

### 상호와 직함은 별개 컬럼이다

프로토타입은 `orgLine.split(' · ')[0]`으로 상호를 만든다. 상호에 ` · `가 들어가면
잘리고, 직함만 있는 고객은 상호가 이상해진다.

스키마에 `company`와 `role_title`이 **이미 따로** 있다. 각각 받아서 각각 저장해라.
**합쳐진 문자열을 받아서 쪼개지 마라. 합쳐서 내려보내지도 마라** — 표시용 결합은
클라이언트가 한다.

### 전화번호

`phone_e164`는 **여기서 바꾸지 마라.** 그게 고객의 정체성이고
`ux_customers_phone`으로 대화와 묶여 있다. 번호가 바뀌면 다른 고객이다.

마스킹은 표현 계층이 한다. 저장은 항상 E.164 전체다.

### 무엇을 보냈는지와 무엇을 비웠는지

`{ "company": "" }`(빈 문자열로 지우기)와 필드를 아예 안 보낸 것(안 건드림)을
**구분해라.** 구분하지 않으면 이름만 고치려다 상호가 지워진다.

## 수용 기준

1. `npm run check` 통과
2. 쿠키 없이 호출 → 401
3. **stale `version` → 409, 그리고 행·필드가 전혀 안 바뀜.**
   두 세션이 같은 카드를 열고 순서대로 저장하는 실제 시나리오로 확인해라
4. 성공 후 `version` 증가
5. **필드가 id로 갱신된다** — 필드 3개 중 가운데를 지운 뒤 나머지를 수정해도
   의도한 행이 바뀐다 (인덱스 기반이면 여기서 깨진다)
6. 같은 `key`로 필드 추가 → 409/400 (500 아님)
7. **상호에 ` · `가 들어가도 온전하다** (`(주)가나 · 다라` 같은 값)
8. 이름만 PATCH → 상호·직함이 유지된다
9. `company`를 `""`로 명시 → 지워진다
10. `phone_e164` 변경 시도 → 거부되거나 무시된다. 절대 바뀌지 않는다
11. 변경 1건당 `events` 1건, 409일 때 이벤트 0건
