## 목표

인박스 **목록 조회 API** 하나. `GET /api/conversations`.

이 슬라이스가 프론트엔드의 가장 큰 결함을 닫는다 — 지금 목록은 **모든 대화의
모든 메시지를 브라우저 메모리에 올려놓고** 필터링·집계한다.

## 지금 무엇이 틀렸는가

`src/state/selectors.ts`를 읽어라. 다섯 함수가 전부 전체 스캔이다:

- `visibleList` — 보관·담당범위·상태·검색을 메모리에서 거른다
- `statusCounts` · `scopeCount` · `archivedCount` — 전수 순회
- `preview` — `c.messages[c.messages.length - 1]`. **목록을 그리려고 모든
  대화의 전체 메시지 배열이 필요하다**

그리고 **칩 숫자와 목록이 어긋난다.** `statusCounts`는 보관함까지 세는데
`visibleList`는 보관을 제외한다.

## 만들 것

`GET /api/conversations` — 목록 + 패싯 집계 + 커서.

쿼리로 받을 것: 보관 여부, 담당 범위(전체/내담당/미배정), 상태, 검색어, 커서, 개수.

응답에는 최소한:

- 대화 배열 — 각 항목에 고객(이름·상호), **미리보기**, 마지막 메시지 시각,
  **이 사용자 기준 안읽음 수**, 담당자, 상태, 라벨, 보관 여부, `version`
- 다음 커서
- **패싯 집계** — 상태별·담당범위별·보관

정확한 필드 이름과 모양은 `shared/wire/conversation.ts`에 정의해라
(지금 스텁이다). 프론트엔드가 나중에 이걸 그대로 쓴다.

## 반드시 지킬 것

### 패싯 집계 — 칩과 목록이 어긋나지 않게

**각 카운트는 자기 차원만 빼고 나머지 필터를 전부 적용해 센다.**
보관 여부는 **항상** 적용된다.

예: 상태 필터가 `미처리`이고 담당범위가 `내담당`일 때
- 상태별 카운트 → 담당범위·보관은 적용, 상태는 미적용
- 담당범위별 카운트 → 상태·보관은 적용, 담당범위는 미적용

이렇게 해야 "미처리 5"를 눌렀을 때 실제로 5개가 나온다.

**카운트 쿼리와 페이지 쿼리를 하나의 `batch()`로 보내라.** 따로 보내면 그
사이에 데이터가 바뀌어 숫자와 목록이 어긋난다.

### 안읽음 — 사용자마다 다르다

`conversations.inbound_count`와 `conversation_reads.read_inbound_count`의
차이로 센다. **메시지를 세지 마라** — 대화당 O(1)이어야 한다.

읽음 기록이 없는 사용자는 전부 안읽음이다.

### 미리보기 — 저장하지 말고 조인해라

`conversations.last_message_id`가 포인터다. 메시지 본문을 조인해서 가져와라.
**미리보기 텍스트를 별도 컬럼으로 저장하지 마라** — 두 번째 진실이 된다.

### 페이지네이션 — 커서

`OFFSET`을 쓰지 마라. 새 메시지가 들어오면 순서가 밀려 항목이 중복되거나 빠진다.

`(last_message_at, id)` 복합 키로 커서를 만들어라. ULID라 id 정렬이 곧 시간
정렬이다. 커서는 클라이언트가 해석할 수 없는 형태로 인코딩해라.

### 검색

고객 이름·상호·전화번호로 찾는다. 전화번호는 E.164로 저장돼 있고 사용자는
`010-1234` 처럼 입력할 수 있다 — **입력을 정규화해서 비교해라.**

## 스키마 참고

`migrations/0001_init.sql`을 읽어라. 관련 테이블은 `conversations`,
`customers`, `messages`, `conversation_assignees`, `conversation_reads`,
`users`다. **마이그레이션을 수정하지 마라.**

인덱스가 이미 있다 — 활성·보관 각각에 `(office_id, last_message_at DESC)`.
`EXPLAIN QUERY PLAN`으로 그게 실제로 쓰이는지 확인해라.

## 수용 기준

1. `npm run check` 통과
2. 쿠키 없이 호출 → 401
3. **패싯 카운트가 목록과 일치한다** — 상태 필터를 걸었을 때 그 상태의
   카운트가 실제 결과 수와 같다. 여러 필터 조합으로 확인해라
4. **보관 여부가 카운트에도 적용된다** (기존 결함: 칩은 보관함까지 셌다)
5. **안읽음이 사용자별이다** — 사용자 A가 읽어도 B의 안읽음이 그대로
6. 커서로 두 페이지를 받았을 때 **중복·누락 0**
7. 페이지 사이에 새 메시지가 들어와도 **이미 본 항목이 다시 나오지 않는다**
8. 전화번호를 `010-1234` 형태로 검색해도 찾아진다
9. `EXPLAIN QUERY PLAN`이 의도한 인덱스를 쓴다
10. 메시지 테이블 전체 스캔이 없다 — 대화 100건에 메시지 1000건을 넣고
    쿼리 수가 대화 수에 비례하지 않는지 확인해라

## 만들지 말 것

- 대화 상세, 메시지 페이지 — 다른 슬라이스 소유
- 상태·담당자 변경 — 다른 슬라이스 소유
- 프론트엔드(`src/`) 수정 — 화면 연결은 나중 슬라이스가 한다.
  `selectors.ts`도 건드리지 마라
- `migrations/`, `wrangler.jsonc` 수정
