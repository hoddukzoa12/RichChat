## 목표

고객 카드의 **내부 메모**. 고객에게 보이지 않는, 직원끼리 남기는 기록이다.

```
POST   /api/conversations/:id/notes
PATCH  /api/conversations/:id/notes/:noteId
DELETE /api/conversations/:id/notes/:noteId
```

조회는 상세 API(B7)가 함께 내려준다. **여기서 목록 엔드포인트를 만들지 마라.**

## 지금 무엇이 틀렸는가

메모에 **id가 없고** 작성자가 **표시 이름 문자열**이다.

id가 없으니 배열 인덱스로 수정한다 — 다른 직원이 메모를 추가하면 인덱스가
밀려 **엉뚱한 메모가 덮인다.**

작성자가 이름이라 **프로필에서 이름을 바꾸면 과거 메모의 작성자 판정이 깨진다.**
동명이인이면 남의 메모를 지울 수 있다.

## 반드시 지킬 것

### 작성자는 id다

`notes.author_id`가 `users(id)` FK다. **이름 문자열로 비교하지 마라.**

`author_id`는 **세션에서** 온다. 요청 본문에서 받지 마라.

응답에는 `authorId`와 표시용 이름을 함께 내리되, **권한 판정은 언제나 id로** 한다.

### 남의 메모는 못 고친다 — SQL에서 막아라

```sql
UPDATE notes SET body = ?, updated_at = ?
 WHERE id = ? AND conversation_id = ? AND author_id = ? AND deleted_at IS NULL
```

**403은 `meta.changes === 0`으로 판정**한다. 먼저 조회해서 작성자를 확인한 뒤
수정하면 그 사이에 바뀔 수 있고, 조회 결과로 메모의 존재 여부가 새어나간다.

**"없음"과 "남의 것"을 응답에서 구분하지 마라.** 구분하면 어떤 메모가 있는지
탐색할 수 있다.

관리자가 남의 메모를 지울 수 있어야 하는지는 **정해지지 않았다.** 필요해 보이면
구현하지 말고 `ask`로 물어라.

### 삭제는 소프트 삭제다

`deleted_at`이 있다. **행을 지우지 마라** — 세무 기록이고 보존 기간 설정이 있다.

모든 조회에 `deleted_at IS NULL`을 걸어라. `ix_notes_conv` 인덱스가 그 조건으로
이미 만들어져 있다.

이미 삭제된 메모를 또 삭제 → 0행이므로 **이벤트도 없다.**

### 경로의 대화 id를 확인해라

`:noteId`만 보고 고치면 다른 대화의 메모를 경로만 바꿔 건드릴 수 있다.
**`conversation_id`도 `WHERE`에 넣어라.**

### 빈 메모

공백만 있는 본문을 저장하지 마라. 400으로 거부한다.

## 수용 기준

1. `npm run check` 통과
2. 쿠키 없이 호출 → 401
3. **타인 메모 PATCH → 403, 그리고 본문이 안 바뀜.** 실제로 두 사용자로 시도해라
4. 타인 메모 DELETE → 403, `deleted_at`이 `NULL` 그대로
5. **"없는 메모"와 "남의 메모"의 응답이 구분되지 않는다**
6. 응답에 `authorId`가 있고, **작성자 판정에 이름 문자열 비교가 없다** —
   `users.name`을 바꿔도 자기 메모를 계속 수정할 수 있다
7. 삭제 후 상세 조회에 안 나온다. **행은 남아 있다**
8. 같은 메모 2회 삭제 → 두 번째는 이벤트 0건
9. 다른 대화의 `:noteId`를 경로에 넣으면 404 (교차 접근 불가)
10. 공백만 있는 본문 → 400
11. 변경 1건당 `events` 1건, 0행 변경 시 0건
