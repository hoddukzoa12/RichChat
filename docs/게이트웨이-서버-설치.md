# SMS 게이트웨이 설치 (사무실 서버)

업무폰 9대를 하나의 인박스로 모으기 위한 서버를 사무실 PC에 세운다.
LGU+ 메시지허브를 대체한다.

> **검토 기준** — 서버 `v1.45.4`(commit `54a5fb6`), Android 앱 commit `90d16d9`.
> 앱과 서버가 활발히 개발 중이라 **버전을 고정**하고, 화면 문구가 다르면
> 이 문서보다 실제 화면을 믿어라.

## 무엇을 만드나

```
[받기]  고객 → 업무폰 → (웹훅 직접 발송) → chat.rich-group.kr
                                            ↑ 게이트웨이 서버를 안 거친다

[보내기] chat.rich-group.kr → 터널 → 사무실 서버 → 업무폰 → 고객

[폰 등록·대기] 업무폰 9대 ⇄ sms.rich-group.kr (터널) → 사무실 서버
```

**받는 쪽은 폰이 우리 워커로 직접 쏜다.** 서버가 죽어도 고객 문의는 계속
들어온다. 멈추는 것은 답장뿐이다.

## 준비물

- 사무실 서버 PC (Windows) — 항상 켜져 있어야 한다
- **Docker Desktop** (WSL2 백엔드)
- 이미 설치된 `cloudflared` — LGU+용으로 세운 그것을 그대로 쓴다
- 업무폰 9대

## 1. 작업 폴더와 Compose 파일

저장소를 통째로 받을 필요가 없다. **Compose 파일 하나면 된다.**

```powershell
mkdir C:\SmsGateway
cd C:\SmsGateway
```

`C:\SmsGateway\.env` 를 만든다:

```
DB_PASSWORD=<긴 임의 비밀번호>
DB_ROOT_PASSWORD=<다른 긴 임의 비밀번호>
PRIVATE_TOKEN=<긴 임의 문자열>
```

값 생성:

```powershell
[Convert]::ToBase64String((1..32|%{Get-Random -Max 256})) -replace '[+/=]',''
```

`C:\SmsGateway\docker-compose.yml` 을 만든다:

```yaml
name: sms-gate-app

services:
  backend:
    image: ghcr.io/android-sms-gateway/server:v1.45.4
    environment:
      - GATEWAY__MODE=private
      - GATEWAY__PRIVATE_TOKEN=${PRIVATE_TOKEN}
      - HTTP__LISTEN=0.0.0.0:3000
      - DATABASE__HOST=db
      - DATABASE__PORT=3306
      - DATABASE__USER=sms
      - DATABASE__PASSWORD=${DB_PASSWORD}
      - DATABASE__DATABASE=sms
      - DATABASE__TIMEZONE=UTC
    ports:
      - "127.0.0.1:3000:3000"     # 터널만 쓰므로 랜에 열지 않는다
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy

  worker:
    image: ghcr.io/android-sms-gateway/server:v1.45.4
    command: ["/app/app", "worker"]
    environment:
      - DATABASE__HOST=db
      - DATABASE__PORT=3306
      - DATABASE__USER=sms
      - DATABASE__PASSWORD=${DB_PASSWORD}
      - DATABASE__DATABASE=sms
      - DATABASE__TIMEZONE=UTC
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    # 포트를 열지 않는다 — 외부에서 부를 일이 없다

  db:
    image: mariadb:11.8.8
    environment:
      - MARIADB_DATABASE=sms
      - MARIADB_USER=sms
      - MARIADB_PASSWORD=${DB_PASSWORD}
      - MARIADB_ROOT_PASSWORD=${DB_ROOT_PASSWORD}
    volumes:
      - db-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
      interval: 10s
      timeout: 5s
      retries: 10
    restart: unless-stopped

volumes:
  db-data:
```

> **왜 이렇게 바꿨나**
>
> - 저장소 기본 Compose는 **`capcom6/sms-gateway` Docker Hub 이미지**를 쓰는데
>   최신 서버 릴리스보다 뒤처져 있다. **GHCR의 버전 고정 태그**를 쓴다.
>   `latest`를 쓰지 않는 이유는 업데이트 후 되돌릴 수 없기 때문이다
> - 저장소 기본 Compose는 `DATABASE__PASSWORD=sms` · `MYSQL_ROOT_PASSWORD=root`를
>   **환경변수로 강제**한다. `config.yml`에 긴 비밀번호를 써도 **환경변수가 이긴다.**
>   그래서 비밀번호를 `.env` 한 곳에서만 정의하고 세 곳이 그것을 참조하게 했다
> - 포트를 `127.0.0.1:3000:3000`으로 묶었다. Cloudflare Tunnel만 쓰므로
>   **랜 전체에 3000번을 열 이유가 없다**
> - `worker`의 포트 노출은 지웠다. 필요 없다
> - MariaDB도 유동 태그 `11` 대신 이 문서에서 검증할 `11.8.8`로 고정했다.
>   이후 버전을 올릴 때는 서버 이미지와 DB를 각각 백업·검증한다

## 3. 터널 — 기존 터널에 호스트명을 **추가**한다

**새 터널은 만들지 않는다.** 기존 `lgu-relay` 터널에 hostname을 하나 더 붙인다.

> **기존 `lgu-send` 레코드의 이름을 바꾸지 마라.** 하나의 터널에 여러 hostname을
> 붙일 수 있다. 이름을 바꾸면 문제가 생겼을 때 되돌릴 경로가 사라진다.
> LGU+ 철거(G5) 때 기존 레코드를 지우면 된다.

### 3-1. DNS 추가

```powershell
cd C:\Cloudflared\bin
cloudflared.exe tunnel list
# 출력에서 lgu-relay의 UUID를 확인한 뒤 이름 대신 UUID를 사용한다.
cloudflared.exe tunnel route dns <LGU-RELAY-터널-UUID> sms.rich-group.kr
```

명령 출력의 `tunnelID`가 기존 `lgu-relay` UUID와 같은지 확인한다. 다른 기본
`config.yml`이 있는 환경에서는 터널 이름만 사용하면 잘못된 터널로 DNS가
연결될 수 있다.

### 3-2. ingress에 규칙 추가

`C:\Windows\System32\config\systemprofile\.cloudflared\config.yml`의
`ingress` **맨 앞**에 넣는다. 기존 LGU+ 규칙은 그대로 둔다.

```yaml
ingress:
  - hostname: sms.rich-group.kr
    service: http://127.0.0.1:3000

  # 기존 LGU+ 규칙 그대로 (G5에서 제거)
  - hostname: lgu-auth.rich-group.kr
    service: https://api.msghub.uplus.co.kr
    originRequest:
      httpHostHeader: api.msghub.uplus.co.kr
  - hostname: lgu-send.rich-group.kr
    service: https://api-send.msghub.uplus.co.kr
    originRequest:
      httpHostHeader: api-send.msghub.uplus.co.kr
  - hostname: lgu-file.rich-group.kr
    service: https://mnt-api.msghub.uplus.co.kr
    originRequest:
      httpHostHeader: mnt-api.msghub.uplus.co.kr

  - service: http_status:404
```

```powershell
cloudflared.exe tunnel ingress validate
sc.exe stop cloudflared
sc.exe start cloudflared
curl.exe https://sms.rich-group.kr/health
```

### 3-3. 경로별로 노출을 가른다

폰은 Access 토큰 헤더를 붙일 수 없으므로 **모바일 경로만 열고 나머지는 막는다.**

Cloudflare 대시보드에서 `sms.rich-group.kr`에 대해:

| 경로 | 처리 |
|---|---|
| `/api/mobile/v1/*` | **공개** — 폰이 붙는 곳 |
| `/health` | 공개 (점검용) |
| `/api/3rdparty/v1/*` | **Access 또는 WAF로 차단** — 워커·관리용 |

**전체 API를 열 필요가 없다.** 관리 API(`3rdparty`)가 공개되면 계정
비밀번호만이 유일한 방어가 된다.

> 워커가 발송할 때 `3rdparty`를 불러야 한다. Access를 걸면 워커에 서비스 토큰
> 헤더를 붙여야 하고, 그 부분은 발신 슬라이스(G3)에서 내가 구현한다.

## 4. 첫 폰 등록 — 계정은 여기서 자동으로 생긴다

**서버에 계정을 만드는 명령은 없다.** 바이너리의 명령은 사실상
`start` · `worker` · `health` 뿐이다. **첫 폰이 붙을 때 계정이 자동 생성된다.**

1. 폰에 **SMS Gateway 앱** 설치 (Google Play 또는 GitHub 릴리스)
2. 앱 → **Settings → Cloud Server**
   (버전에 따라 `Private Server`가 별도 메뉴로 안 보일 수 있다)
3. 서버 주소에 **경로까지** 넣는다:

   ```
   https://sms.rich-group.kr/api/mobile/v1
   ```

   **경로를 빼면 동작하지 않는다.** 공식 문서에 명시돼 있다.
4. `.env`의 `PRIVATE_TOKEN` 값을 입력
5. 연결되면 같은 화면에 **자동 생성된 계정 아이디·비밀번호**가 표시된다.
   **안전한 곳에 적어둔다** — 워커가 이 자격으로 발송한다
6. **Device ID**도 표시된다. 적어둔다

## 5. 나머지 8대 등록

같은 계정에 붙인다. 두 가지 방법 중 하나:

- 4단계에서 확인한 **계정 아이디·비밀번호**로 로그인
- 이미 붙은 폰에서 **일회용 로그인 코드**를 생성해 사용 (신뢰도가 낮은 기기용)

**폰마다 반드시 할 것**

- **배터리 최적화 예외** — 안 하면 안드로이드가 앱을 재워 웹훅이 지연된다
- **상시 충전**
- 앱 자동 업데이트 후에도 살아나는지 확인

**등록이 끝나면 표를 만들어 알려달라.**

| 폰 라벨 | 전화번호 | Device ID |
|---|---|---|
| 예: 1팀 업무폰 | 010-0000-0000 | `ffffffff...` |

이 표가 그대로 답장 라우팅 테이블이 된다. **고객이 문자한 그 폰으로 답장이 나간다.**

---

> **현재 설치 중단점** — G1이 실제 배포되고 HMAC Secret 바인딩 이름이 확정되기
> 전에는 여기까지 진행한다. 서버·터널·첫 폰·모바일데이터 연결만 검증하고
> 웹훅 등록은 보류한다.

## 6. 웹훅 등록 — 앱 화면이 아니라 **서버 API로** 한다

앱의 `Settings → Webhooks` 화면에는 **재시도 설정·Signing Key·등록된 목록**만
있고 **URL을 추가하는 UI가 없다.**

서버 API로 등록한다. `deviceId`를 생략하면 **계정의 모든 폰에 적용**되므로
9대에 각각 등록할 필요가 없다.

`/api/3rdparty/v1/*`에는 Access를 적용하므로, 최초 등록은 사무실 서버에서
로컬 원본 주소로 실행한다. 아래 명령은 PowerShell에서 그대로 실행할 수 있게
한 줄로 적었다.

```powershell
curl.exe -X POST "http://127.0.0.1:3000/api/3rdparty/v1/webhooks" -u "<계정아이디>:<계정비밀번호>" -H "Content-Type: application/json" -d '{"id":"richchat-sms-received","url":"https://chat.rich-group.kr/api/hooks/sms-gateway","event":"sms:received"}'
```

> **G1 endpoint 배포와 Worker Secret 입력이 끝난 뒤 등록한다.** 먼저 등록하면
> 폰이 실패한 웹훅을 장시간 재시도한다. 지금 설치할 때는 첫 폰의 외부 연결
> 확인까지 진행하고, 웹훅 등록 직전에서 멈춘다.

**등록할 이벤트** — 우선 `sms:received` 하나만 등록해 시험하고,
슬라이스가 병합되는 대로 나머지를 추가한다.

| 이벤트 | 언제 추가 |
|---|---|
| `sms:received` | G1 배포·Worker Secret 설정 후 |
| `mms:received` · `mms:downloaded` | G2 병합 후 |
| `sms:sent` · `sms:delivered` · `sms:failed` | G4 병합 후 |

> **URL이 `/api/hooks/sms-gateway`다.** 이전 문서에 적었던
> `/api/hooks/gateway`는 틀렸다. 실제 구현된 경로는 위와 같다.
>
> 특정 폰에만 걸 때 필드명은 `device_id`가 아니라 **`deviceId`**다.

## 7. Signing Key — 기본값을 그대로 쓰지 마라

위치는 `Settings → Webhooks → Signing Key`가 맞다.

**그런데 앱이 만드는 기본 키는 8자 NanoID다.** 업무용 HMAC 키로는 짧다.
**32바이트 이상 무작위 값으로 교체해라.**

```powershell
[Convert]::ToBase64String((1..32|%{Get-Random -Max 256}))
```

**전달 방법**

- **채팅에 붙여넣지 마라**
- Git·D1·로그에 평문으로 남기지 마라
- 워커에는 직접 입력한다:

  ```powershell
  npx wrangler secret put SMS_GATEWAY_WEBHOOK_SIGNING_KEY
  ```

  (정확한 바인딩 이름은 G1 배포 때 확정해서 알려주겠다)

**9대로 늘릴 때**

- 간단한 방식: 계정 전체에 **같은 키**를 쓴다. 이 경우 각 폰에 같은 값을
  직접 설정하거나, 인증된 설정 API로 계정 공통 키를 배포한 뒤 반영 여부를 확인한다
- 더 안전한 방식: **폰별 키**를 쓰고 워커 Secret에 `deviceId → key` 매핑을 둔다.
  한 대가 털려도 나머지가 안전하다

**워커가 검증하는 방식** (G1에 이미 구현됨, 확인함)

```
HMAC-SHA256(signingKey, rawRequestBody + X-Timestamp)
  X-Signature   소문자 hex (대소문자 무관하게 처리)
  X-Timestamp   Unix 초
  JSON 파싱 전 raw body 사용
  상수시간 비교
  타임스탬프 ±5분 창으로 재전송 차단
```

## 8. 검증

**① 서버가 산다**

```powershell
curl.exe https://sms.rich-group.kr/health
```

**② 폰이 붙었다** — 앱에 연결됨 표시, 계정에 기기가 보임

**③ 관리 API가 막혔다**

```powershell
curl.exe -sS -o NUL -w "%{http_code}`n" https://sms.rich-group.kr/api/3rdparty/v1/devices
```

판정:

- `302` 또는 `403` — Cloudflare Access에서 차단됨: 정상
- `404` — WAF/Worker에서 의도적으로 경로를 숨긴 경우: 정상
- `401` — SMS Gateway 원본까지 도달함: **경로 보호 안 됨**
- `200` — 인증 없이 관리 API가 열림: **심각한 설정 오류**

**④ 수신이 온다** — 등록한 폰으로 문자를 보내면 인박스에 뜬다 (G1 배포 후)

**⑤ 밖에서도 붙는다** — 폰의 와이파이를 끄고 데이터로 전환해도 연결이 유지되는지.
업무폰이 외근을 나가므로 **이게 되어야 한다**

## 운영

**자동 시작** — Docker Desktop을 "Windows 시작 시 실행"으로.
`restart: unless-stopped`가 걸려 있어 Docker가 뜨면 컨테이너는 따라 온다.
단, Docker Desktop은 일반적으로 Windows **부팅 시점이 아니라 사용자 로그인 후**
시작된다. 무인 재부팅 뒤에도 운영해야 한다면 자동 로그인 또는 별도의 서비스형
운영 구성을 확인하고 실제 재부팅 시험을 한다.

**백업** — D1에는 고객 대화가 남지만, MariaDB에는 계정·Device ID·기기 인증
토큰·웹훅·설정·발송 상태가 저장된다. DB가 유실되면 진행 중 발송뿐 아니라 폰
재등록과 설정 복구가 필요할 수 있다. 업데이트 전에 아래처럼 컨테이너 안에서
덤프를 만든 뒤 호스트로 복사한다.

```powershell
cd C:\SmsGateway
$stamp = Get-Date -Format "yyyyMMdd-HHmmss"
docker compose exec -T db sh -c 'mariadb-dump --single-transaction --routines --triggers -uroot -p"$MARIADB_ROOT_PASSWORD" sms > /tmp/backup.sql'
docker compose cp db:/tmp/backup.sql ".\backup-$stamp.sql"
docker compose exec -T db rm -f /tmp/backup.sql
Get-Item ".\backup-$stamp.sql"
```

생성 파일이 비어 있지 않은지 확인하고, 최초 운영 전에는 별도 임시 DB로 복원
시험까지 한다.

**업데이트** — **버전 태그를 올린 뒤** 적용한다. `latest`를 쓰지 않는 이유가 이것이다.

```powershell
# docker-compose.yml 의 :v1.45.4 를 새 버전으로 바꾸고
docker compose pull
docker compose up -d
```

**업데이트 전에 반드시 백업하고, 수신이 되는지 먼저 확인해라.**
문제가 생기면 서버 이미지 태그를 되돌린다. 단, 새 버전이 DB migration을
수행했다면 이미지 태그만 되돌려서는 복구되지 않을 수 있으므로 필요할 때는
업데이트 직전 DB 백업도 함께 복원한다.

## 알아둘 것

**푸시 알림은 제작자 서버를 경유한다.** 설정의 `upstream_url`이
`https://api.sms-gate.app/upstream/v1`이다. private 모드에서도 폰을 깨우는
신호는 이 경로를 탄다. **본문은 우리 서버에 남는 것으로 보이지만
직접 확인하지는 못했다.**

**사진 발신은 안 된다.** 앱 소스에 `sendMultimediaMessage` 호출이 0건이다.
MMS 수신은 가능하지만 이벤트가 나뉜다. `mms:received`에는 메타데이터만 오고,
다운로드 완료 후 `mms:downloaded`에 본문과 Base64 첨부가 실려 온다.

**통신사 대량발송 제한.** 개인 회선이라 하루 발송량 제한과 스팸 필터가 있다.
응대 규모면 대체로 괜찮지만 **회선 정지 위험이 0은 아니다.**

**폰이 단일 장애점이다.** 꺼지거나 인터넷이 끊기면 그 번호의 문의를 못 받는다.
9대로 나뉘어 있어 전체가 동시에 죽지는 않는 것이 그나마 낫다.
